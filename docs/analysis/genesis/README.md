# Genesis: stamp a whole Geldar environment from a GitHub Actions workflow

Ledger for the campaign. Written 2026-11-14 by the geldar coordinator `geldar-3b` after interviews with geldar-93 (deploys and the node), geldar-ops (Body and the CD), geldar-registration (register, owner API, supervisor) and scriptorium-orchestrator (kit and player hosts), a read of the repo and the sibling repos, and online research. Status (2026-11-15): **wave G0 mostly merged, G1 in progress**; the card states are in the Ledger at the top of [packets.md](packets.md). The plan is in [plan.md](plan.md), the cards in [packets.md](packets.md), the architecture decision in [0188](../../decisions/0188-genesis-environment-stamp.md) (Proposed).

## The owner's goal

"We must be able to do a full genesis of our infra from CI. Paper, plug-ins, configs, bodies, MCP, everything must be accounted for and deployable from the repo. I want to get to a point where we can do full stamps of a geldar environment from an actions workflow." (2026-11-14)

Owner answers taken in this session:

- Stamp targets: **rebuild production from nothing**, **a second independent environment**, and **an ephemeral stamp inside CI**. A cloud VM target was not chosen.
- Outside systems: the workflow **automates DNS records and the Entra sign-in app** too. The gateway firewall and port forward stay a checked prerequisite (not selected).

## Exit criteria

The campaign ends when the exit run in [plan.md](plan.md) section 9 passes, not when the packets merge:

1. A `workflow_dispatch` stamp of a **new environment on a clean host** reaches a green verify (stack health, a bot joins through the proxy, MCP and register answer, schema at head, NATS round trip) with no step done by hand except the listed human prerequisites.
2. A **re-stamp of the same environment is a no-op** (plan mode reports no drift; apply changes nothing).
3. A **restore drill** rebuilds Postgres, JetStream state and the world from backups into a fresh stamp and passes the same verify.
4. An **ephemeral CI stamp** runs on a hosted runner on every change to the stamp surface and on a schedule.
5. **Production is described by the same definition** as the other environments; a drift report between the live node and its definition is empty or every difference is recorded and accepted.
6. No secret, account name or address is in the repo; every credential the workflow holds is listed with its scope and holder ([plan.md](plan.md) section 6).

## Rules this campaign holds

- Nothing changes the live node except through the existing deploy window process (geldar-93). A stamp of production is a rebuild into a **spare** host, then a cutover the owner approves; it never rebuilds the live host in place.
- "We approve PRs, not CI or CD" (geldar-93): the stamp workflow is `workflow_dispatch` only, behind GitHub Environment protection (required reviewer), and a change to the workflow needs the owner's PR approval.
- The live `nats-auth.conf` is never regenerated by a desktop run (registration, geldar-93). Stamping generates the file on the **target**, create-if-missing, and an existing node is **adopted**, not rewritten.
- Plugin jars, Paper, Velocity, Caddy and NATS changes still wait for an owner-approved window (restart rules); a stamp of a **new** host is not a restart of the live one.
- Principle 1 holds: nothing here lets a human act inside the world.

## Decisions

| id | Question | Status | Answer used by the cards |
|---|---|---|---|
| D-GN-01 | Targets | **Decided** by the owner, 2026-11-14 | Production rebuild, second environment, ephemeral CI stamp |
| D-GN-02 | DNS and Entra automation | **Decided** by the owner, 2026-11-14 | Automated, with the scopes in plan.md section 6; gateway firewall stays a checked prerequisite |
| D-GN-03 | Is creating the host in scope? | **Decided** by the owner, 2026-11-14 | A stamp starts from a clean Debian host with SSH. For the test environment the owner wants a **Hyper-V Debian VM on node 3**, created by a card (G3-04) run from an operator machine that holds the node 3 SSH key; CI never holds that key. "Fresh install with no dependencies pre-installed" is the bar: the bootstrap installs everything |
| D-GN-04 | Where do per-environment secrets live? | **Decided** by the owner, 2026-11-14 | Generated on the target host (create-if-missing, never rotated silently). Only secrets that must outlive a host (the Entra client secret, the backup key) are also kept in a per-environment Azure Key Vault |
| D-GN-05 | Where does the second environment run? | **Decided** by the owner, 2026-11-14 | A new Hyper-V VM on node 3, used for testing. Same-host staging beside production is not planned |
| D-GN-06 | Do ranger kit hosts belong to this campaign? | **Decided** by the owner, 2026-11-14 | No: world side only. The owner also wants **a real ranger connected on the test world** as the final acceptance. That is a **human step after the stamp** (a subscription login), run on scriptorium's side against the test environment; the stamp itself verifies with a scripted test player (D-GN-10) |
| D-GN-07 | Does a stamp hold a subscription login or call a model? | Proposed: **no** | CI never calls a model (scriptorium D-SC-01); players start only after a human step |
| D-GN-08 | Deploy channel | Proposed | GitHub-hosted job to the target over a forced-command SSH key, plus the existing self-hosted runner path kept for the live node until cutover |
| D-GN-09 | Whether `geldar-infra` becomes the home of the Azure pieces | **Decided** by the owner, 2026-11-14 | No: in this repo under `deploy/genesis/azure/` for now |
| D-GN-10 | What does the stamp's automated mind check use? | Proposed (follows from D-GN-06 and D-GN-07) | A scripted test player: a disposable token, a scripted client that joins through the proxy and acts through MCP, no model. The real-ranger check is the owner's acceptance, outside CI |
