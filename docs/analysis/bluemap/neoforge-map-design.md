## 2. How the Paper map works today, and the NeoForge equivalent
Paper today: BlueMap inside Paper renders into the paper-data volume under `bluemap/web`. `bluemap-web` (Caddy, loopback :8100, GET/HEAD only, read-only subpath mount) serves tiles; `/maps/*/live/*` is proxied to `bluemap-alias` (name-to-alias rewrite, fail closed), which talks to Paper's BlueMap web server on :8101. The host edge Caddy (`deploy/caddy/map.caddy`, `map.{$GELDAR_DOMAIN}`) proxies to `{$GELDAR_MAP_UPSTREAM}`; kill switch `map-off.caddy`. TLS is the edge's.

NeoForge equivalent:
- **Render live inside the server**, same as Paper. Output goes to `<neoforge data volume>/bluemap/web`. A second `bluemap-web` Caddy container (new service name, loopback port other than 8100, e.g. 8110) mounts that subpath read-only. Same Caddyfile minus everything that needs the alias proxy.
- **No live JSON at all.** Set `live-player-markers: false`/players hidden (BlueMap plugin config `player-markers` off, `hide-*` all) and have the web container serve no `/maps/*/live/*` path (404, not proxied). No alias proxy for this shard. This removes the whole name/position surface (section 3).
- **Edge:** new site file `deploy/caddy/map-neoforge.caddy` for `map.neoforge.{$GELDAR_DOMAIN}` with `{$GELDAR_MAP_NF_UPSTREAM}`, plus `map-neoforge-off.caddy`. Copy of map.caddy with the same 405, header stripping and nosniff.
- **Window steps (owner-gated, executed by ops via geldar-93):** (1) back up the running edge config; (2) stage the new site file; (3) `caddy validate` in a throwaway container; (4) load and `caddy reload`; (5) check `https://map.neoforge.<zone>/` 200 and POST 405; rollback: restore the backup, reload (or swap in the off file). Order: web container and mod first, edge last, DNS after.
- **Render mode:** live in-server, low priority. Offline CLI would need a volume copy and 25+ GB of extra disk for no benefit.
- **Budget** (neoforge container: 3 CPU, 12 GiB, heap 9G, up to 100 players): `render-thread-count: 1`, `update-interval` default, `full-update-interval: 0`, `region-file-check-interval` raised (e.g. 30), `hires`-only, explicit map bounds (min/max) around the played area, no full render without the owner's word. Measured on Paper: one thread, whole-world render is the dominant cost; the first bounded render should be timed (start/end stamps) by ops. Heap is the real risk: BlueMap holds region data in memory, so geldar-neoforge must confirm headroom under 9G (a 12 GiB container leaves about 3 GiB off-heap). If headroom is thin, set `render-thread-count: 1`, bounds small, or fall back to offline CLI in a separate capped container (`cpus: 1`, `mem 2g`) rendering a snapshot.
- **Web container limits:** as Paper: 0.25 CPU, 64m, 64 pids, read-only root, cap_drop ALL.

## 3. Privacy and safety (humans are real people)
- No player markers, names or positions: players hidden in BlueMap config AND the web container returns 404 for all `/maps/*/live/*`. Two independent layers; a test asserts the 404 on the real Caddy (as bluemap-web.test.ts does for Paper).
- No chat panel, no follow feature, no dial script wiring on this map (those are Paper-shard features). The page serves BlueMap stock plus no custom scripts, so `settings.json` needs no pin and no BM-16c machinery. (The dial could be added later; it needs a clock feed the NeoForge shard does not have.)
- No markers of any kind until the owner says (builds can reveal player homes; ask first).
- Hidden content: BlueMap's own `hide-*` and `min-y` options; consider `remove-caves-below-y` so underground bases are not rendered. Flag to the owner: a map shows every build, including private ones.
- Caching: Caddy `Cache-Control` as in the Paper Caddyfile (tiles revalidate; settings no-cache). Rate limits: Caddy has no limiter built in; the edge cap is request body 1 KiB, GET/HEAD only, container CPU cap. If abuse appears, add Cloudflare rate rules at the zone (owner action), not code.

## Addendum 2026-11-18 (answers from geldar-93, checked against origin/main compose)
- **Image:** `compose/nf-live.yml` service `neoforge` uses `itzg/minecraft-server:2026.10.1-java25@sha256:d12aed7e35981dfe259b60fbfee77d23a19b5898a7a31dca298d18b47b7b5776` (Java 25, digest pinned). Limits 3 CPU, 12288m, `MEMORY` 9G (`NF_NEOFORGE_HEAP`). Data volume `neoforge-data` mounted at `/data`; the geldar jar is a read-only bind at `/geldar/mods/geldar-neoforge.jar`, copied into `/data/mods` by the entrypoint after a sha256 check (`GELDAR_NF_MOD_SHA256`). BlueMap should reuse that mechanism (second jar, same check), owned by geldar-neoforge.
- **Exactly what the web container mounts:** only the volume `neoforge-data` with `subpath: bluemap/web`, read-only, at `/srv` (same form as Paper's `paper-data` subpath). Not `/data` itself: world, `server.properties`, RCON password and mod configs are never visible to it. The directory must exist before the web container starts, so the web service `depends_on` the neoforge service healthy and ops creates nothing by hand. Plus the Caddyfile bind, read-only.
- **Extra heap (estimate, to be measured):** one render thread, bounded maps, hires only: about 0.5 to 1 GiB of live heap while rendering (region and mesh buffers), near 0.2 GiB idle, plus about 100 to 200 MiB off-heap. It lives inside the existing 9G heap (no change to `-Xmx`); the container limit leaves 12 - 9 = 3 GiB off-heap, of which idle use today is about 6.2 - heap in use. Measure: container RSS and GC log during the first bounded render at 0 players, then with players. If RSS plus 1.5 GiB approaches 11 GiB, lower bounds or render offline in a separate capped container (1 CPU, 2 GiB).
- **Scratch-first compatibility test (before any live step):** `deploy/scratch/scratch.sh` with `SCRATCH_PLATFORM=neoforge`, same image digest, with the geldar jar as today and the BlueMap jar as a second mod mounted the same way (hash checked by the script before up). Steps for ops: bring the scratch stack up; read the neoforge log for `BlueMap` lines; wait for `Server started`; check `bluemap/web/index.html` exists in the scratch volume; run `/bluemap` status; bounded render of a small box; fetch a tile through a scratch web container. **Failure shapes:** (1) mod skipped: log shows an incompatible-mod / "requires neoforge" / missing dependency message, server starts, no `bluemap` directory, no web files; (2) crash: loading error screen text in the log, "Mod loading has failed", the server exits (compose restart loop); (3) loads but no render: exception stack from `de.bluecolored` classes in the log, `/bluemap` unknown. For (1) and (3) players are unaffected; (2) is why live must wait for a clean scratch run. Pass criteria: no exception from bluemap or geldar classes, server reaches started, tile file written, RSS recorded.
- **Paper precedent reused:** the owner's map is exposed through the host edge Caddy site `deploy/caddy/map.caddy` (`map.{$GELDAR_DOMAIN}`, GET/HEAD only with 405, drops client address headers, 1 KiB request body, nosniff, no-referrer, frame-ancestors none, `reverse_proxy {$GELDAR_MAP_UPSTREAM}`) in front of the loopback `bluemap-web` container; kill switch `map-off.caddy`. The new site copies that file with its own upstream variable and its own off file, so conventions, headers and the validate script are the same; only the upstream differs and there is no live proxy behind it.
