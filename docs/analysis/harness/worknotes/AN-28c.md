## Per-break and per-pickup cost with the flag off

- Per break (`BlockChangeListener.onBreak`): the existing `record(block, null)` runs as before. The new branch evaluates
  `enabled.getAsBoolean()` (already read before this change) and then `provenanceEnabled.getAsBoolean()`, which is
  `setup.enabled && setup.provenance`: two volatile reads, short-circuit at `provenance == false`. No `sendBreakProvenance`,
  no JsonObject, no allocation. `sink` and `tick` are not touched.
- Per pickup (`PickupProvenanceListener.onPickup`): Bukkit dispatches the event to this listener (it is registered
  whatever the flag). The first line is `if (sink == null || !enabled.getAsBoolean()) return;`: one volatile read, then
  return. No `instanceof`, no thrower lookup, no publish, no allocation.
- Nothing is added to the server tick path. The `provenance` read is the only new field access.

## Where this role table is used

Get-NatsUsers (geldar.ps1, line 391 on this branch) is called only by `Initialize-NatsAuth` (geldar.ps1, line 345), which
writes `compose/secrets/nats-auth.conf` for `./geldar.ps1 shard nats-auth <name>`. The scratch seed user and the colo
table come from the same function. `deploy/nats-auth-nf.ps1` has its own `Get-NfNatsUsers`, which is NOT generated from
geldar.ps1 and is NOT changed by this packet.

Per environment (whether its deployed auth file CHANGES on merge, and who regenerates it):

- **phase0 scratch** (`shard nats-auth phase0 --local` or `--scratch`, `docs/runbooks/scratch-stack.md`): the conf is
  generated per run in a temp or export directory. A new run after merge gets the new body entry. An existing conf
  is not regenerated (Initialize-NatsAuth writes it only when missing), so an old scratch conf keeps the old body entry
  until it is deleted. Regenerated by the operator or the scratch runbook.
- **colo** (`shard nats-auth colo`, `compose/nats-auth.yml` overlay, `docs/runbooks/colo-deploy.md`): the live file
  `compose/secrets/nats-auth.conf` on the node is NOT changed by merge. The generator writes it only when missing.
  colo-deploy.md (lines 86 to 93) says a NATS config change is manual: `manual NATS config changed: not applied`, and
  `docs/runbooks/nats-auth-inplace.md` is the procedure (SIGHUP, backup first, by hand).
- **nf-live** (`deploy/nats-auth-nf.ps1`, `compose/secrets-nf/nats-auth.conf`, `compose/nf-live.yml`): NO change. Its
  table is `Get-NfNatsUsers` in deploy/nats-auth-nf.ps1, which does not read geldar.ps1, and the nf conf is never
  overwritten (`kept ... never overwritten`). The nf body user has no provenance grant; provenance is Paper-only.
- **other**: none found. The repo-checks fixtures (`nats-auth-fixtures.ts`) and the live test are mirrors, not deployed files.

RESUME (`docs/analysis/sheet/RESUME.md`) names the live NATS change as operator work: the card's sentence is "The live
server's NATS conf change is applied by the operator by hand (`docs/analysis/sheet/RESUME.md`); nothing is switched on
there." Nothing in this packet changes a live file. The live `body` user keeps its old grants until the operator applies
a conf change by hand under `docs/runbooks/nats-auth-inplace.md`.

## Overlay switch

There is no switch in the generator: Initialize-NatsAuth does not read `compose/nats-auth.yml`, `colo.yml` or `config.yml`
(the test `the table has no overlay switch` checks the function text and two renders). The compose overlay only mounts
the conf. So "byte-identical with the overlay off" is tested as "two renders match apart from passwords"; the table is
the same whatever the compose overlays are.
