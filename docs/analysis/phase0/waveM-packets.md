## (a) Architecture

The real server, `threshold/mcp` (`@geldar/mcp`), keeps the mock's contract exactly: the same 14 tools from `@geldar/contract`; one HTTP session per player at `/p/<player_id>`; the same per-tool validation, result-size cap and trimming; the same wake policy, imported from `@geldar/mcp-mock` rather than copied. It replaces the mock's simulated world with the real Body channel:
- **`look`, `wait`, `act`, `say`, `read_book`** go to the ranger's Body over core NATS request/reply on the wave 5 subjects, plus one new `book` subject.
- **`wait`** reads the `GELDAR_EVENTS` JetStream stream through one ordered consumer; a per-life event log turns events into the player's events; the cursor is the stream sequence number, so it survives a restart.
- **Validation of `act`** uses the same output validator Adam's thoughts go through (`animus/src/validate`); plans are built with `buildPlan` (`animus/src/loop/plan.ts`).
- **Postgres** holds owners, players, hashed tokens, budgets and the journal mirror, in a new migration applied by the first migration runner.
- **Bodies:** each ranger is one Node Body process (`golem/src/players/`) built from wave 5's `startAdamBody`, `BodySupervisor` and `managerAcquire`; username = life id; registered in the life registry and whitelisted over RCON before it connects; started and stopped by a presence record the MCP writes.
- **Hosting:** the MCP runs as a hardened container in a compose overlay (nothing published except `127.0.0.1:<port>` for local use); the public tunnel is deferred (correction 1).
- **Players:** six rangers plus a `test` player (`ag-test-01`, used only by the live cases). Adam stays headless: animus never serves the rangers' lives and the MCP never serves Adam's.

## Wave M conventions (every packet)

- **Contract first.** New messages go through schemas in `contract/`; regenerate, never hand-edit. The MCP tool vocabulary (interests, wake reasons, player event types) is **frozen** for Wave M.
- **Unit tests use fakes only.** `*.it.test.ts` run only when `GELDAR_IT=1`; live cases are written in the packets and run by the orchestrator at wave end; failure messages print the state seen.
- **Hostile world text:** speech, sign, book and journal text appear only inside `untrusted_world_text` with the fixed `note` (decision 0034); event texts, error messages and tool descriptions are fixed templates and never echo world text; logs never carry tokens, `Authorization` headers, request bodies, world text or `reasoning`.
- **Identity comes from the transport:** the player from the URL plus the verified token, the life id from Postgres; nothing the client sends picks a life; every NATS subject is built through `contract/src/subjects.ts`.
- **No model call anywhere in our code** (spec 5.15.1); the scripted stub client in tests drives the MCP SDK client with no model.
- Files under 500 lines; briefs at most about 12 items; at 80 turns a coder commits what is done and reports what remains; coders edit only inside their own worktree, use the Edit tool, no backtick escapes in PowerShell strings.

## Design: how each tool reaches the Body

| Tool | Body channel | Cost | Notes |
|---|---|---|---|
| `look` | `SnapshotRequest{reason:'mcp_look'}` on the life's snapshot subject (5 s) | free | Always a fresh snapshot, never cached. Through `play-view`: `heard` lines move to `untrusted_world_text.speech` (newest 40), sign `text` moves from `notable_blocks` to `signs`, `events_since_last_thought` is emptied (the event log is the source), budget and `days_since_sleep` set from Postgres. |
| `wait` | Event log plus one snapshot at return | free | See the wait rules. |
| `act` | `SnapshotRequest{reason:'mcp_act'}`, then `PlanMessage` on `.plan`, then a `PlanAck` (2 s; link timeout 5 s) | 1 per accepted `say`, action and intent | The `act` input is the contract's `ActInput` (Appendix C `intent` and `actions`). It becomes `Thought{reasoning, say, intent, actions}` validated by `createOutputValidator` with the shard bounds (Phase 0 allow-list: verbs `goto mine craft place eat sleep open deposit withdraw attack wait`; programs `travel gather craft rest flee`). `buildPlan` assigns ids, generation, revision, `expires_tick` (+1200). Snapshot and plan run under a per-player lock (revision window 2); one retry on `stale_snapshot`. Result indices: say first, then actions, then intent. **The action list is atomic**: if any action fails validation, every action is rejected (the bad ones with their code, the rest `batch_rejected`). A refused ack rejects every item with its reason and refunds the credits. |
| `say` | A `PlanMessage` whose thought holds only `say` | 1 | Waits up to 5 s for the `plan_result` event: `spoken = said`; else `spoken:false, reason:'unconfirmed'`. The Body's voice guard strips control characters and refuses a leading `/`. One per 3 s. |
| `read_book` | New `BookRequest` on `geldar.<shard>.body.<life>.book` | free | The Body reads the held written book, else the first carried one; returns `{title, author, text <= 8192}` which goes only into `untrusted_world_text.book`. No book: ToolError `no_book`. |
| `sleep` | A plan with `{do:'sleep'}`, then up to 15 s for the `plan_result` | free | Returns the digest since the last sleep mark (at most 100 events) and the journal mirror under `untrusted_world_text`. |
| `status` | Postgres plus the event log | free | Days alive, days since sleep, laws none in Phase 0. |
| `journal` | Postgres `mcp_journal`, plus a `sovereign_call` event | free | Keeps the last 8192 characters per life. |
| `write_book`, `define_skill`, `use_skill`, `offer`, `propose`, `vote` | none | 0 | ToolError `not_available: That does not exist in this world yet.` All 14 tools stay listed with their contract schemas. |

**Wait rules.** `max_seconds` is clamped to `sovereign.mcp.wait_cap_seconds` (240); the hard deadline adds a snapshot fetched with a 3 s timeout, so a `wait` returns within about 245 s, inside the client's 300 s. Waking reuses the mock's `evaluateWake` unchanged (priority order, `wake_on` filtering, `interests`, minimum spacing `sovereign.wake.min_spacing_seconds` (30), the `intent_run_too_long` fallback). **The cursor is the acknowledgement:** a waking candidate is any event with a sequence above the cursor the client passed; if a response is lost, the client retries with its old cursor and the event wakes again, so no waking event is ever dropped; an event held back by spacing wakes at the end of the window or is delivered in the `events` of a `timeout` result. `fitResult(..., 16000, wakingSeqs)` keeps the waking events, their speech lines and `wake_reason` (decision 0034, overnight row 11). A second `wait` for the same player ends the first at once with `timeout`. Every 25 s the server sends a notification on the request's stream (progress if the client sent a token, else `notifications/message` debug) to keep the stream alive. Body unreachable at return: ToolError `body_unavailable`, cursor not advanced.

**How events become player events** (`threshold/mcp/src/events/mapper.ts`; fixed templates only, never copying `detail`): `speech` (`own:false`) -> `speech` classified by animus `classifySpeech` (`directly_addressed`; overheard lines only in `conversation_digest`); `speech` `own:true` skipped; plugin `damage` and `wake` with `unexpected_damage` or `reflex_danger` -> `damage` (`unexpected_damage`); `wake` `new_agent_within_N` -> `agent_approached` (only while an intent with that `wake_on` runs); terminal `intent` events -> `intent_finished` (`goal_completed`, `precondition_failed`, `intent_run_too_long`); `plan_result` with immediate actions -> `intent_finished` "Your actions finished: N done, M failed"; `wake` `no_plan` -> `intent_finished` "Your intent ended: your body restarted." (`precondition_failed`; vocabulary unchanged, Q12); plugin `death` -> `damage` "You died and woke at spawn." (`unexpected_damage`); `reflex_fired` -> `reflex` (suppressed); plugin `sleep` -> `reflex` "You slept." (moves `days_since_sleep`); `day_night` (new; published by the MCP from the world clock, deduplicated by `(shard, day, phase)`) -> fanned out to every ranger log (`day_night`).

**Budget (spec 5.7, 5.15.3).** Each life has a balance in `mcp_budget`; accrues `sovereign.budget.credits_per_real_hour` (30) up to `cap_credits` (240) in one SQL `UPDATE ... RETURNING`; a call reserves its cost before the plan is sent under an atomic `credits >= n` guard and is refunded for anything the Body refuses; at 0 credits each item is rejected `budget_exhausted` and `look`, `wait`, `status` still work. Every `act`, `say`, `journal` and `sleep` publishes a `sovereign_call` event (tool, accepted and rejected items, credits, `thought_id`, the player's own `reasoning`, `say` and journal text, never world text). No `thoughts` row is written (no model runs on our side).

## Design: identity and tokens

- Token format `gmcp-` plus 64 hex characters (256 random bits); the fixed prefix lets the repo secret scan catch a leak. Only `mcp-tokens token mint <player> --out <file>` makes tokens: it writes `GELDAR_MCP_TOKEN=<token>` to a file only the current user can read, refuses any path inside the repo, never prints the token (only the `tk_` id); at most 2 active tokens per player (rotation); default expiry 30 days.
- Storage: `token_hash = HMAC-SHA256(pepper, token)`; the pepper is the secret file `compose/secrets/mcp-token-pepper.txt`; lookup by hash then `timingSafeEqual`; never stored in plain text.
- Checks on every request: scheme exactly `Bearer `, header at most 512 bytes, token matches the pattern, active (not revoked, not expired), player active, harness enabled, token's `player_id` equals the URL's. Unknown player or bad token: 401 with `WWW-Authenticate: Bearer`; a valid token for another player: 403. A hit is cached 5 s; a miss never cached.
- Revocation: `token revoke` sets `revoked_at`; a trigger sends `NOTIFY mcp_token_revoked`; the server LISTENs, closes the player's session and ends its open `wait` with `session_revoked` within about 1 s.
- Limits: per player 60 calls a minute, `act` at most every 2 s, `say` every 3 s, one open `wait`, 4 concurrent requests; per owner 600 calls a minute; owner cap enforced by `player add` and re-checked at authentication; failed authentication 30 a minute per client address and 300 a minute globally (429 with `Retry-After`). Body at most 64 KiB; JSON-RPC batch arrays refused; any `Origin` header gets 403; `Host` must equal the configured public host or the loopback/dev address; `headersTimeout` 10 s; at most 128 connections; results capped at 16 KiB.
- Replay: a bearer token can be replayed until revoked; TLS (when public), short expiry, revocation and rate limits bound the damage; a stolen token reaches only that one player through the same validator and budget.
- Logs: one JSON line per request (`at`, `event`, `player_id`, `token_id`, `tool`, `status`, `latency_ms`, `bytes_in`, `bytes_out`); a test scans every log line for a token canary.

## Design: multi-Body hosting

- One Node process per ranger: `node --max-old-space-size=320 golem/src/players/main.ts --player <id>`; `geldar.ps1 players up|down|status|logs` spawns them with PID files in `.geldar/players/`; each reuses `BodySupervisor`, `managerAcquire` and `startAdamBody` and builds the `AdamConfig` shape from `sovereign.players[]`, so wave 5's `adam/` files are not edited; a book server (WM-07) runs beside the `MindLinkServer`.
- Usernames are life ids (decision 0040), at most 16 characters: `ag_jason_01`, `ag_zack_01`, `ag_billy_01`, `ag_trini_01`, `ag_kimberly_01`, `ag_tommy_01`, plus `ag_test_01`. Launcher player ids use hyphens (correction 2). `mcp_players.life_id` points at the current life.
- Before connecting: the `ConnectionManager` registers the username; the host first runs `whitelist add <life_id>` over RCON (infrastructure use allowed by threat-model rule 9).
- Presence: the MCP writes `PresenceRecord` to the KV bucket `geldar-presence`: *awake* while a `wait` is open or a call came within 60 s; *dim* after that; *hibernating* after 10 minutes with `desired_body: down`. The host watches its key: `up` starts the supervisor (new generation, resuming from the checkpoint), `down` stops it (the bot logs out; an offline player is frozen and safe). A call for a hibernating player sets `up`, then waits up to 20 s for a snapshot before failing with `body_unavailable`. No "seal in" step in Wave M (Q8).
- Capacity on the desktop (measured in the wave test): six ranger Bodies about 150 to 250 MB each; the MCP container at most 512 MB; Adam's stack as today; six Scriptorium kit containers about 0.4 to 0.8 GB each (their side); plan for 4 to 7 GB more RAM than Adam alone. Bodies use no GPU. Spawn the rangers away from Adam (Q11).

## Design: public hosting (deferred; owner chose loopback first)

When the stack moves to the colo the options stay: a Cloudflare Tunnel (outbound only, ingress rule forwarding only `^/p/[a-z][a-z0-9-]{1,38}$`, edge WAF and rate limit, mind the 100 s proxied-response timeout so the 25 s keepalive must be proven, Bot Fight Mode and challenges off for the hostname), Tailscale Funnel (no domain needed, no edge limits), or a port-forward (rejected: exposes the home network). The threat-model changes (first off-host exposure, internet actor path limited to `/p/*`, the human's CLI boundary, NATS and Postgres reachable from code execution in the MCP, Cloudflare as a trusted party, token leakage, denial of service) are written into `docs/threat-model.md` by WM-10 so the review happens before the move.

## WM-13: Player skins (added 2026-11-09 at the owner's request; depends on WM-01 and the velocity-identity plugin)

Goal: each sovereign player (the six rangers now; the TNG crew and bring-your-own-skin players later) shows its own skin to every client and to BlueMap.

- **How skins work here.** Life-id accounts are not Mojang accounts, so the proxy must supply signed skin textures. The Velocity identity plugin (`plugin/velocity-identity`) adds a `textures` profile property (value and signature) on login for a registered life id; Velocity modern forwarding passes it to Paper, so clients and BlueMap see it. Textures must be signed by Mojang: get them by uploading the skin PNG to a signing service (MineSkin) once, then cache the returned value and signature.
- **Config.** `sovereign.players[].skin: {file, model: classic|slim}` in `shards/phase0.yaml`; the PNG lives outside the repo (the repo is public and fan skins carry the creators' rights): a gitignored `skins/` directory or the player's own private repo. Signed values are cached in a secrets file or a KV bucket `geldar-skins`, never committed.
- **Pieces.** (1) `tools/players-cli skin set <player> <png> [--model slim]`: validates a 64x64 (or legacy 64x32) PNG (size cap, no extra chunks), uploads it to the signing service, stores value and signature; (2) the identity plugin reads `geldar-skins` and sets the property for life ids it knows, fail open (no skin) if absent; (3) tests: PNG validation, the plugin sets the property only for the registered life, no skin leaves the default; a live case: two rangers connect, a third client sees both textures.
- **Owner inputs.** The six PNGs (character names in decision 0052); a MineSkin API key; a yes to sending the PNGs to that third-party service.
- **Later.** Bring-your-own-skin: the same command, driven by the launcher or the player's own repo; the TNG crew is the same list with more entries.
