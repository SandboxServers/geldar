# W6-20 worknote: the smoke run's `body` abort

Run `smoke-20261110T121408Z` (life `ag_smoke_01`, fast tier, wave6-main c93ba3f) aborted at minute 6 with
rule `body`. Every sample from minute 1 had `animus`, `body` and `lantern-local` false, while `ollama`,
`postgres`, `nats` and `paper` were true and thoughts kept arriving.

## Cause (code)

The three process probes never matched their own processes.

- `tools/adam-cli/src/run.ts` spawned each service with its relative entry (`src/main.ts`, `src/adam/main.ts`)
  and the package directory as the working directory. Windows records the command line as given, so the
  process table showed `node.exe src/main.ts`. Checked on this machine: a child started that way reports
  exactly that command line.
- `tools/adam-run/src/adapters.ts` (`observe`) and `tools/adam-run/src/safe-stop.ts` (`ownership`) matched
  `golem/src/adam/main.ts`, `animus/src/main.ts`, `lantern-local/src/main.ts`. Those strings never appear
  in the command line, so `alive.animus`, `alive.body` and `alive['lantern-local']` were false on every
  sample. The Body probe had a second fault: it also required the word `body` in the command line, which no
  entry contains.
- Consequence 1: `sustained(... !bodyConnected, 300000)` fired the `body` rule after five minutes of samples,
  that is at minute 6. The Mind was alive and producing thoughts; the probe was blind.
- Consequence 2: the safe-stop orphan check classed every real service process as `other`, so its
  `orphans: pass` in the abort record proves nothing.

The fixtures in `safe-stop.test.ts` used `node animus/src/main.ts`, a command line the
spawn never produces, so the suite could not catch the mismatch.

Fix (commit `fix(adam-run): the probe finds the Body, the Mind and the Lantern by their entry`):
- `adam-cli/src/procs.ts` `entryPath` gives the absolute entry; `run.ts` `startService` spawns with it.
  Test: `procs.test.ts` "spawns each service from its absolute entry".
- `adam-run/src/safe-stop.ts` `SERVICE_ENTRY` and `serviceAlive` match each service by its own entry;
  `adapters.ts` uses `serviceAlive`. Test: `safe-stop.test.ts` "serviceAlive".
- Revert check: `SERVICE_ENTRY.body` mutated to `golem/src/adam/xmain.ts` fails the serviceAlive test;
  `entryPath` mutated to return `service.entry` fails the entry-point test. Both files were restored from
  scratchpad copies and `git diff --stat` was empty.

Hypotheses checked:
1. "adam-run start does not start the Body for the new life id": not the cause. `adam up` starts the three
   services for any life; the life id only selects SQL rows and the whitelist/username. The Body was started; the probe could not see it.
2. "connectivity keyed to a hard-coded ag_adam_01/02": not the cause. `lifeId` is used only in the SQL
   of `observe`; the `body` rule reads `alive.body` only.
3. "the Body started but could not join (whitelist, username)": not established. The Body's log and the
   Paper log for the run are not in the run folder and nothing is running now, so the join was not observed.
   The probe bug alone explains the `false` samples. Ops should still check, after a fresh run with the fix,
   the Paper log for `ag_smoke_01` joining (`docker logs --tail 200 <paper container>`, no secrets printed).

## Report and status fixes (follow-up)

Each item has a failing test first and a revert-check (one line mutated, test fails, file restored, `git diff --stat` empty).

- (a) Committed in `73015ce`. `adapters.ts` `reportRun` and `cli.ts` `stop` read `started_at`, the key
  `manifest.ts` writes. Before, every report failed with `manifest.json has no startedAt`, and `stop` fell
  back to the current time, so the safe-stop ownership test saw every process as `other`. Tests:
  "the reporter passes the run folder and the manifest to adam-report" (adapters.test.ts) and
  "reads started_at from the manifest, so a service started in this run is owned and signalled" (cli.test.ts).
  Manifest fixtures in the tests now use `started_at`.
- (b) Committed in `4f3b4b4`. `status` and `report` without `--run-id` take the newest `<profile>-<UTC stamp>`
  folder under `.geldar/runs` (`cli.ts` `latestRunId`, listed through the harness port `runFolders`). They no
  longer build the id from the current time. If the profile has no run folder, they print
  `no <profile> run under <runs root>` and exit 1. Tests: "status and report without --run-id" (cli.test.ts).
- (c) Committed in `1815989`. A run whose `abort.json` exists but whose manifest has no `started_at` prints
  `state: aborted before the run started`, the rule, the reason, and every abort criterion as UNKNOWN
  (`cli.ts` `abortedBeforeStartText`). `report` does not call the reporter for such a run, and `stop` prints
  `the run is already aborted; nothing to stop`. Tests: "a run aborted before it started" (cli.test.ts).
- Not changed: `stop` with no `--run-id` still builds its id from the current time, as `start` does. The
  packet named only `status` and `report`; `stop` needs the same latest-folder rule if it is to be used without a run id.

## Ops

No manual ops step is needed for the abort itself. After this fix merges, start a new smoke run from a fresh
`adam up`; the old run folders keep the wrong `alive` values and should not be used as evidence.
