# W6-04: Velocity readiness marker ordering

## Diagnosis (before the fix)

Source: `plugin/velocity-identity/src/main/java/dev/geldar/identity/IdentityPlugin.java`, at base `130f2df`.

The startup sequence in `onProxyInitialization`:

1. Register the `geldar:cmd` channel.
2. Write the readiness marker (`ReadyMarker.forThisProcess(READY_FILE).write()`).
3. Log "Geldar identity enabled".
4. Schedule the denial summary.
5. Read the NATS URL; if it is unset or blank, log an error and return.
6. Start the life registry client and the skin client.

Defect: step 2 runs before step 5 and before any NATS connection exists. The marker therefore reports readiness in three cases where the plugin cannot serve a login:

- `GELDAR_NATS_URL` unset: no client is ever created, the life registry never syncs, `LoginGate` denies every name. The healthcheck (port open and marker matches `/proc/<pid>/stat`) still passes.
- NATS unreachable or the life-registry bucket absent: `RegistryClient` retries with backoff; the gate stays closed; the marker stays.
- NATS connection lost later: `RegistryClient.onConnectionEvent` calls `markUnsynced`, which closes the gate, but nothing removes the marker. The marker is removed only at `ProxyShutdownEvent`.

The marker's pid and start-time format was already correct (E-N9 fixed the shell side of the check). The defect is the ordering and the missing removal on lost sync.

How the plugin handles a lost connection: fail closed at once. `markUnsynced` closes the gate immediately; there is no grace window in the plugin. Reconnect uses backoff (500 ms doubling to 5 s) and a full replay on each reconnect. The only tolerance is the compose healthcheck's retry budget (12 retries at 10 s), so a disconnect shorter than about two minutes does not turn the proxy unhealthy.

## Fix

- New `ReadinessFeed` wraps the life registry's feed. `markSynced` writes the marker (after the registry has synced); `markUnsynced` removes it; `retire()` (proxy shutdown) removes it and blocks any later write.
- `IdentityPlugin` no longer writes the marker in `onProxyInitialization`. The life-registry client is built on the wrapper. With an unset URL no client exists, so no marker is ever written.
- Readiness depends on the life registry only. The skin registry is not a readiness condition: a failed skin lookup keeps the default profile and never affects admission.
- A write failure logs an error and leaves no marker; the gate does not depend on the marker (unchanged).

Tests: `ReadinessFeedTest` (absent before sync, present after sync, removed on disconnect, rewritten on reconnect, failed write does not stop the feed, nothing written after retire, the registry still receives the sync) and `IdentityPluginTest.aMissingNatsUrlNeverWritesTheMarker`.

## Revert-checks

- Early write restored (`lifeFeed.markSynced();` before the URL check, which writes the marker and is a no-op for the gate with no replay in progress): `aMissingNatsUrlNeverWritesTheMarker` fails at its `assertFalse`.
- Disconnect removal dropped (`markUnsynced` no longer calls `removeMarker()`): `theMarkerIsRemovedWhenTheConnectionIsLost` fails.

Both were restored from a scratchpad backup; `git diff --stat` was empty afterwards.

## Not changed (outside the packet's file list)

- `compose/phase0.yml` line 130 says the plugin "writes /tmp/geldar-identity.ready at init". After this fix it is written when the life registry syncs. The healthcheck command itself is unchanged and still correct. The comment needs a follow-up edit under a packet that owns `compose/`.

## Live verification for ops

- Restart the velocity container. Expect `unhealthy` (or `starting`) until NATS is up and the life-registry bucket has replayed, then `healthy`.
- With NATS stopped, the marker is removed when the connection is lost (the registry event, not a poll); the healthcheck then fails after its retry budget.
