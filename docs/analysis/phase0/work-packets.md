# Phase 0 work packets

Ledger and status: [README.md](README.md). Process: [campaign-packet skill](../../../.claude/skills/campaign-packet/SKILL.md).

## Dispatch rules (every packet)

Each packet is self-contained: the coder skips CLAUDE.md, so these rules travel with it.

1. Work only in the worktree named in your brief. PowerShell 7 only. Run every pnpm command as `./geldar.ps1 pnpm <args>` from the worktree root: it puts the pinned pnpm on PATH, including for scripts that call pnpm again (plain `corepack pnpm typecheck` fails on those). In a new worktree run `./geldar.ps1 setup` first.
2. Create or change only the files your packet lists. Never edit `docs/spec.md`, generated code, or another packet's files.
3. Pin exact versions, only the ones the packet names: `./geldar.ps1 pnpm add -E -D <pkg>@<version> --filter <package>` (drop `-D` for a runtime dependency). Images by digest: resolve with `docker buildx imagetools inspect <image>:<tag>` and write `<image>:<tag>@sha256:<digest>`.
4. TypeScript: ESM, `.ts` import specifiers (`import { x } from './x.ts'`), no enums, namespaces or parameter properties (`erasableSyntaxOnly`). Each package's `tsconfig.json` extends the root `tsconfig.base.json` by relative path (`../tsconfig.base.json` for a top-level package). Tests are `*.test.ts` under `src/` or `test/`, run by the root `pnpm test`.
5. Files stay under 700 lines (soft cap 500). No `utils.ts` or `helpers.ts`. LF line endings. No secrets, account names, or public or private-network IPs (`127.0.0.1` is fine); passwords and secrets are Docker secret files in `compose/secrets/` (gitignored, generated by `./geldar.ps1 shard secrets`), never environment values; non-secret settings live in `.env` (gitignored) with working defaults in `.env.example`.
6. Run the packet's checks in order, ending with `./geldar.ps1 check` from the worktree root. Five fix rounds per check at most, then stop and report.
7. Confirm each new test fails without the change it guards (revert locally, run, restore) and say so in the report.
8. Commit as soon as checks pass, with the message in your brief; WIP commits are squashed into one (see packet-coder.md). Never `git stash`, `git push`, `gh pr` or `git worktree prune`.
9. Report to the path in your brief; return one line: `<packet> <done|blocked|failed> <commit-sha|-> <report-path>`.
10. Budget: the packet should fit about 40k tokens, but wave 1 coders used 60k to 95k and three ran out of context before committing. Read each file once, pipe long output through `Select-Object -Last 20`, and commit as soon as `./geldar.ps1 check` passes; write a short progress note to the report path after the first working step, so a continuation coder starts from facts. Use the exact commit message and trailer lines in the brief, unchanged.
11. Batch review (owner ruling, wave 2): packets that run in parallel (P0-08a, 08b, 09a, 09b; then P0-10a, 10b, 10c) are not reviewed one by one. When all coders in the batch have committed, merge them into a temporary review branch `phase0/wave2-batch-<name>` off `phase0/wave2` and run ONE full, thorough review over the combined diff (cross-packet collisions, registry blocks, shared arena and world state, live-test interference, plus each packet against its spec). Fix passes go to fresh coders per packet or one coder for the batch; re-review the batch up to 5 rounds (not 3) before asking the owner. Single packets keep the 3-pass loop.

## Wave close (every wave)

A wave is not done when its last packet ships. Before the wave PR is merged, and as part of that PR, the orchestrator runs the wave close:

1. **Docs.** A docs sweep: the files that describe what the wave changed (README, `sql/README.md`, skills such as `run-shard` and `body-bench`, the threat model, `docs/decisions/` records for anything that departs from the spec) match the code. A fresh `packet-coder` does it from a list the wave reviewer writes (the wave review already checks "docs that no longer match"); the orchestrator never edits outside `docs/analysis/phase0/`, `.claude/state/` and branch state.
2. **Retro.** The orchestrator writes `docs/analysis/phase0/retro/wave-<N>.md`: what shipped, what cost the most agent passes and why (read the reviewer verdicts), what the reviews caught that tests did not, what went wrong in the process (agents out of context, tool limits, Windows quirks, brief mistakes), what to keep, and numbered **Actions**, each with an owner (a packet, a skill edit, an agent edit, a CI check) and a size.
3. **Process packet.** A `W<N>-process` packet applies the Actions that change the development process or AI SDLC scaffolding: `.claude/skills/`, `.claude/agents/`, `CLAUDE.md`, `AGENTS.md`, `tools/repo-checks`, CI, packet and brief templates. It is written like any packet (files, tests or checks, commit subject), goes through the same review loop, and merges into the wave branch. Actions that need an owner decision are asked, not guessed.
4. **Ledger.** `README.md` records the retro and the process packet; `RESUME.md` names the next wave.

The retro Actions must be small and checkable. A process change that does not make the next wave cheaper or safer is dropped, not kept.

## Contract (what packets build against)

**Workspace.** Root `package.json` scripts: `lint`, `typecheck` (runs each package's `typecheck`), `test` (one Vitest run), `check:repo`, `check:generated` (runs each package's `check:generated`). `pnpm-workspace.yaml` already lists `contract`, `golem`, `animus`, `lantern-local`, `eventsink`, `glass`, `tools/*`.

**`@geldar/contract` layout** (created by P0-01, extended by P0-02 to P0-04):

```
contract/
  package.json            name @geldar/contract, "type": "module", "exports": { ".": "./src/index.ts" }
  tsconfig.json           extends ../tsconfig.base.json, include ["src", "scripts", "test"]
  schemas/<name>.schema.json      the source of truth, JSON Schema draft 2020-12
  scripts/generator.ts    exports generate(): Promise<Map<path, text>> and findStale(): Promise<string[]>
  scripts/generate.ts     CLI only: node scripts/generate.ts           -> writes src/generated/*
                                    node scripts/generate.ts --check   -> exits 1 and lists files that differ
  src/generated/types.ts          generated: one exported type per schema (json-schema-to-typescript)
  src/generated/validators.js     generated: Ajv standalone ESM, one export per schema
  src/generated/validators.d.ts   generated: declarations for validators.js
  src/index.ts            hand-written: re-exports the types and one typed function per schema
  test/<name>.test.ts     fixtures that must pass and must fail
```

Each schema file has `"$schema": "https://json-schema.org/draft/2020-12/schema"`, `"$id": "https://geldar.dev/schemas/<name>.schema.json"`, a `"title"` in PascalCase (it becomes the TypeScript type name), and `"additionalProperties": false` on every object. Shared definitions live in `common.schema.json` under `$defs` and are referenced as `"common.schema.json#/$defs/<Name>"`.

`src/index.ts` exports, per schema, the type and a validator:

```ts
export type { Snapshot } from './generated/types.ts';
export function validateSnapshot(value: unknown): ValidationResult<Snapshot>;

export type ValidationResult<T> =
  | { ok: true; value: T }
  | { ok: false; errors: string[] };   // "<instancePath> <message>", e.g. "/self/health must be <= 20"
```

`src/index.ts` has one marked block per packet (`// --- P0-01 snapshot ---`, `// --- P0-02 thought ---`, `// --- P0-03 records ---`, `// --- P0-04 thinker ---`), created empty by P0-01. Each later packet fills only its own block. P0-02, P0-03 and P0-04 run in parallel and all regenerate `src/generated/*`, so those files conflict when the wave branch merges them: the orchestrator resolves by keeping every block in `index.ts`, taking either side of each generated file, rerunning `./geldar.ps1 pnpm --filter @geldar/contract generate`, and committing the result. Coders don't resolve these conflicts.

**The action outcome shape** (P0-07c writes it; 08 and 09 return it). Every handler returns an `ActionOutcome`; `runAction` turns it into the object stored in `ActionRecord.result` plus the record `state`:

```ts
type FailReason = 'invalid_args' | 'timeout' | 'blocked' | 'not_found' | 'out_of_reach' | 'missing_materials'
  | 'missing_station' | 'not_possible' | 'interrupted' | 'unsupported' | 'internal';
type ActionOutcome =
  | { status: 'completed'; detail: Record<string, JsonValue> }
  | { status: 'failed'; reason: FailReason; message: string; detail: Record<string, JsonValue> }
  | { status: 'cancelled'; detail: Record<string, JsonValue> };
// stored in ActionRecord.result (snake_case, plain JSON, no undefined values):
//   { status, reason?, message?, latency_ms, world_ticks, detail }
// world_ticks = world-age ticks the action took (bot.time.age delta), or null if unknown. Wall time and world ticks
// are separate clocks (spec 5.14); the benchmark needs both because latency in ms changes with the tick rate.
// ActionRecord.state: completed -> 'completed', failed -> 'failed', cancelled -> 'cancelled'.
```

`blocked` is a reason, not a status: the spec's "abandon with `blocked`" is a failed action whose reason is `blocked`. `ActionRecord.result` is an unconstrained object in the contract, so the contract cannot check the inside of it; the shape above is Golem's until the Body executor (wave 4) needs it stored, and that wave decides whether to promote it to a contract schema. Packets prove the shape by building a full `ActionRecord` around it and passing `validateActionRecord`.

**Actions are the contract's `Action` verbs.** Handlers receive a contract `Action` already validated (`validateThought({ reasoning: 'x', actions: [action] })` inside `runAction`), typed as `Extract<Action, { do: K }>`. The verb for "gather" is `mine`; the container verbs are `open`, `deposit`, `withdraw` with `at: Position`. Execution may use any world knowledge Mineflayer has (for example `findBlocks` over loaded chunks); this ignores the spec's "authorized perception" rule (5.2), which applies to what the snapshot tells the Mind and is built in wave 4. **Timeouts are scaled.** Wall-clock timeouts are multiplied by `ctx.timeScale` (`20 / target TPS`, default 1); stall and "path blocked for more than 30 s" rules count **world ticks** (600 ticks), not milliseconds.

```ts
}
```
