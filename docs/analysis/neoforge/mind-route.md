# How to connect the Mind to a NeoForge shard

Status: design note, 2026-11-17. Nothing here was run. Every fact is from the repo at the base of this branch unless marked UNVERIFIED. Read with [RESUME.md](RESUME.md) and [p0-body-model.md](p0-body-model.md) (section 10).

## 1. Goal and what "connected" means

The owner's goal: a working golem Body on the NeoForge server, with a Claude Mind in the world with the owner when the owner tests. "Connected" means all of these hold:

- A Claude Mind (the scriptorium kit's session, on a Mind host) drives one Body on the NeoForge server through geldar-mcp, using the MCP tools over HTTP.
- The Mind sees only the MCP text it gets back from its tool calls. Nothing in the Mind's context says it is being watched, observed or recorded.
- Telemetry (OTLP traces, logs, metrics, the eventsink) never reaches the Mind: no MCP tool returns it and the Mind's container has no telemetry endpoint set.
- The owner can see the Body in the world with a human Minecraft client, and the Mind's actions appear there.

Not in scope here: P3 to P8 (event export, block-owner log, BlueMap, progression), and any change to the live autonomous shard.

## 2. How the live Mind route works today

The live Colo shard already has this route on paper. Each hop, with the file that declares it:

1. **Mind host** (scriptorium session, a VM the owner's scriptorium orchestrator runs) sends `https://mcp.<domain>/p/<player_id>` with `Authorization: Bearer <player token>`. Source of the route: `docs/siblings/scriptorium.md` ("How a sovereign player reaches Geldar"), `deploy/caddy/mcp.caddy`.
2. **Shared Caddy** (`board-proxy`, node) serves the site. `deploy/caddy/mcp.caddy` allows GET, HEAD, POST and DELETE only (`/p/<player_id>` only), caps the body at 64 KiB, strips client-supplied forwarding headers and sets `x-geldar-client-ip`. The upstream is `GELDAR_MCP_UPSTREAM`, which `deploy/colo-public.sh` writes as `127.0.0.1:<port>` in the node's env file. Installing the site is `deploy/colo-public.sh install mcp`.
3. **geldar-mcp** (`compose/colo.yml`, service `geldar-mcp`, published on `127.0.0.1:8788` only; source `threshold/mcp`). It checks the bearer token by HMAC under the MCP token pepper, looked up in `mcp_tokens` in Postgres. A token binds to one player; a token on another player's path gets 403. Its NATS user is `mcp`. The Host allow-list and the Origin refusal are in `threshold/mcp/src/http/front.ts` (Origin is refused, any Origin).
4. **NATS** (`compose/colo.yml`, service `nats`, no published port, colo network only). geldar-mcp publishes `sovereign_call` and reads presence under the `geldar.<shard>.body.>` subjects, per `docs/security/authn-authz-map.md` (NATS users table).
5. **The Body.** The sovereign route runs through `players-host` (`compose/colo.yml`, profile `sovereign`): "one Body per sovereign ranger, started by the player's presence record". `golem-body` is the house Body (`GELDAR_MC_HOST: velocity`, port 25565). Which of the two a Mind's `sovereign_call` ends in is UNVERIFIED from the repo; the brief's chain named golem-body, and this note corrects it to players-host for sovereign players.
6. **Velocity** (`compose/colo.yml`, service `velocity`, itzg/mc-proxy, bot ingress `127.0.0.1:25567` mapped to 25565). Velocity is the only game listener; Paper's game port is not published.
7. **Paper** (or NeoForge on the scratch variant) behind Velocity's modern forwarding, with the geldar-velocity-identity plugin.

Credentials, by role (names and locations only, no values):

| Role | Used by | Where it lives |
|---|---|---|
| Player MCP bearer token (`gmcp-` plus 64 hex, 90 days) | the Mind host, one per player | minted by `tools/mcp-tokens`; the Mind host's token file (location set by the scriptorium kit; UNVERIFIED for this repo) |
| Token pepper | geldar-mcp, register, admin | a compose secret file; `GELDAR_MCP_PEPPER_FILE` |
| `geldar_mcp` Postgres role password | geldar-mcp | `GELDAR_MCP_DB_PASSWORD_FILE` |
| NATS passwords (`mcp`, `body`, `mind`) | geldar-mcp, golem-body and players-host, animus | generated by `./geldar.ps1 shard nats-auth <shard>`; `GELDAR_NATS_PASSWORD_FILE` |
| Velocity forwarding secret | Paper and Velocity | a compose secret; the Velocity side reads it at start |
| RCON password | Paper, players-host, admin one-shot | a compose secret |
| Owner API key (`gowner-`) | account owner's scripts | never accepted by the MCP endpoint; not part of this route |
| Ingest token (OTLP) | Mind host telemetry SDK | Caddy env file (`GELDAR_INGEST_TOKEN`) and the Mind host; a separate route, not the MCP path |
| Scriptorium dev token | the scriptorium dev seam only (section 4A) | a separate dev token file, not yet defined in this repo (see section 7) |

Per-role secret rules are in `docs/security/secrets-by-role.md`; a leak of the token pepper ends every token, so rotation is an operator step.

What each hop needs, in short: the Mind host needs an https endpoint and a player token; Caddy needs `GELDAR_MCP_UPSTREAM` and the `mcp` site live; geldar-mcp needs its Postgres role, pepper and NATS user; NATS needs the users and the shard's subjects; the Body needs its NATS user and a reachable Velocity; Velocity needs the forwarding secret.

## 3. What exists on the scratch NeoForge stack today

Source: `docs/runbooks/scratch-stack.md` (NeoForge section), `compose/opt-in/scratch-neoforge.yml`, `compose/phase0.yml`, `deploy/scratch/nf.env`.

- Services: postgres, nats, paper (NeoForge 26.1.2 build 126 with Proxy Compatible Forge 1.3.1), velocity, eventsink. Overlay selected by `SCRATCH_PLATFORM=neoforge`, suffix `nf`.
- The P0 probe: a golem script joins the server through Velocity. Runs 1 to 4 brought the stack up; the probe itself is still to run (RESUME, "Run 5"). Results are in `p0-findings.md`.
- Ports are loopback only (`deploy/scratch/nf.env`). RCON is published on loopback in this variant only.
- No geldar-core jar is mounted, so the eventsink sees no game events.
- Missing for a Mind: **golem-body** (only in `compose/colo.yml`), **geldar-mcp** (same), **players-host** (same), a **mind-side client** of any kind, the **MCP listen address and dev token file**, and a **player record** in the roster and tokens for the test player. The scratch stack has no Caddy, so no https route at all.
- Missing for the human client: nothing in the scratch stack exposes Velocity beyond loopback, and a vanilla 26.1 client join is unverified (RESUME, P0 unverified).

## 4. Options

### Option A: the P0b shape on the desktop, with the dev seam

Extend the scratch NeoForge stack with golem-body, geldar-mcp and players-host (copies of the colo service blocks with scratch names, ports and secrets). Run it on the owner's desktop, as the scratch stack already can (its runbook has a desktop path for the NATS auth files). The MCP port is published on `127.0.0.1` only. The scriptorium session runs in a container on the same desktop and reaches the MCP through the dev seam: `GELDAR_DEV_MCP_URL` as http, host `host.docker.internal`, a port from 1024 to 65535, one player while the variable is set. The owner's Minecraft client connects to the loopback Velocity port.

- Pros: no node change, no public exposure, no Caddy, no DNS, no token on the node. Fastest path to a Mind test. The seam already exists in the scriptorium kit.
- Cons: the Mind and the owner's client are on one machine, so the test does not prove remote reach. The seam takes one player only. The MCP Host allow-list must be extended for the dev port (scriptorium doc: the Docker host alias and loopback on the dev port; UNVERIFIED in this repo). A new compose project is needed on the desktop. The NeoForge download from the desktop is UNVERIFIED (the node and the Mind VM cannot reach the NeoForge Maven host).
- Node changes: none.
- Repo paths touched: `compose/opt-in/scratch-neoforge.yml` or a new overlay, `deploy/scratch/` (env file), `threshold/mcp` (dev listen address and Host list, if needed), `docs/runbooks/scratch-stack.md`. Paths that auto-deploy on merge to the node (colo-images list: `golem/`, `eventsink/`, `tools/admin/`, `contract/`, `sql/`): only if the packet touches them. `threshold/` (the geldar-mcp image) is not on that list in the brief; whether it auto-deploys is UNVERIFIED, so check before merging.
- Approvals: owner's go to run the desktop stack and the NeoForge download; owner's go to mint one test player token; no public exposure, no DNS, no Caddy.
- Effort: about one packet (P0b) plus one owner-run session. Estimate, not measured.

### Option B: a second compose project on the Colo node as the final NeoForge instance

A separate project (own Velocity, NeoForge Paper, golem-body, players-host, geldar-mcp, eventsink, and its own NATS and Postgres or a separate database). The MCP is reached through the shared Caddy by a second host name (for example `mcp-<name>.<domain>`), and the game port is reached by the human client through a tunnel or a proxy.

- Pros: the Mind reaches the Body over the same https route the scriptorium design uses, so the test proves the route. A real remote host.
- Cons: the node is the live autonomous shard's host. Adding a host name changes the shared Caddy: a file under `config/geldar/` plus one `docker restart board-proxy` (the admin API is off on the node, so reload does not work; that restart is a short outage for every site, estimate only). Ports must not be 25565 or 25566, and the node's rules forbid publishing those. A human client needs a public or tunnelled game port, which the RESUME says needs a separate approval. NATS and Postgres: sharing with the live shard risks cross-shard subjects and rows; a separate instance costs more memory on a node with budgets already set (live caps are in `compose/colo.yml`).
- Node changes: a new compose project directory, env file, secrets (generated by `gen-secrets` and `shard nats-auth` for the new shard), a Postgres role and database, a migration run, a Caddy site file and restart, and a DNS record (owner action).
- Repo paths touched: `compose/` (new project file), `shards/` (a new shard file), `deploy/caddy/` (new site file), `deploy/` scripts, `tools/mcp-tokens` (roster and tokens), plus the colo-images paths above when merged.
- Approvals: owner (DNS name, the Caddy host, the public or tunnelled game port, token minting, the node window); operator (the compose project, secrets, migration, Caddy restart). The node's operator rules say ops agents do not run sudo steps.
- Effort: several packets and one approved node window. Estimate, not measured.

### Option C: hybrid (recommended)

Run Option A on the desktop first to get a Mind into a world with the owner. Then write the final instance as Option B, but only after the owner decides the human route and the public name. A is a rehearsal of the same service set, so B reuses its compose blocks and the test plan in section 6.

Recommendation, in three lines:
1. Do A now on the desktop: it gives a Mind in the world with the owner without touching the node or exposing a port.
2. Write B as a design, not a deploy, and hold it until the owner decides the human route and the public host name.
3. Treat the Hall/shard2 design as another owner's: any second-shard overlap (NATS, Postgres, Caddy host) is an open item for the lead, not a change in this note.

Per option, what is touched and who acts:

| | Repo paths | Node | Operator / lead | Owner approval |
|---|---|---|---|---|
| A | compose overlay, `deploy/scratch/`, possibly `threshold/mcp` (dev Host), runbook | none | none on the node; the owner runs the desktop stack | desktop run; one test token; NeoForge download |
| B | `compose/`, `shards/`, `deploy/caddy/`, `deploy/`, `tools/mcp-tokens`; colo-images paths on merge | new project, secrets, migration, Caddy file, `board-proxy` restart | operator: compose, secrets, migrate, restart; lead: schedule | DNS name; public or tunnelled game port; token minting; the window |
| C | A now, B later | as B, later | as B, later | as A now; as B later |

## 5. The final NeoForge instance: what "fully reachable" needs

Design inputs only. Nothing here is a decision.

- **Game port for the human client.** Either a tunnel from the owner's machine (no public port) or a public port other than 25565 and 25566. The tunnel is the lower-exposure choice; both need the owner's approval.
- **MCP host for the Mind.** One host name through the shared Caddy, with its own upstream and the same `mcp.caddy` rules, or the dev seam for a desktop Mind (no public host).
- **Glass and BlueMap.** Public read-only sites exist for the live shard. A second instance would need its own upstreams and host names, and BlueMap is P5 (on hold). Out of scope for the first test.
- **Shared with the live shard:** the Caddy process and its env file; the DNS zone; the node's CPU and memory budget. Recommended shared only as far as the Caddy restart.
- **Separate from the live shard:** Velocity, the NeoForge Paper, the world volume, the forwarding secret, RCON, the NATS server (or a separate subject scope), the Postgres database, the MCP service and its pepper, the eventsink. The live autonomous shard must stay untouched; a separate compose project and project name is the boundary.
- **Known NeoForge issues to carry:** the mc-proxy image runs Velocity as root with `UID` set (RESUME, lessons; live does the same, a deploy change is owner's); the PCF config owner (uid 1000 on a mode 600 file) against the Paper user (1001), cause unverified; no geldar-core jar, so no game events.

## 6. Test plan: a Claude Mind in the world with the owner

Minimal path (Option A): desktop scratch stack up with golem-body, players-host and geldar-mcp; one test player in the roster and one token minted; the scriptorium session given the dev seam URL and that token; the owner's client joins Velocity on loopback.

Checks, in order. Each has a pass condition and needs a run record:

1. **Stack health.** Every service healthy; no published port other than loopback; no 25565 or 25566 (`deploy/README.md` section (g) rule, applied to the desktop too).
2. **Auth refusal.** `curl http://127.0.0.1:<port>/p/<player>` with no token returns 401, not a connection error (same check as `deploy/README.md` section (g)). With a token for another player, 403.
3. **MCP tools list.** The Mind's session lists the MCP tools; the list matches `docs/reference/mcp-tools.md`. Tool names are not repeated here (UNVERIFIED against the current build).
4. **Look.** One look through MCP returns the Body's view as plain text. The owner's client shows the same Body in the world.
5. **Goto.** One goto through MCP moves the Body; the owner sees it move. Check the position text in the MCP reply against the server (RCON read-only `data get` or `execute if` only).
6. **Plain text only.** Grep the Mind's transcript and every tool result for telemetry field names (trace ids, span names, OTLP keys) and for any observer or recording wording. The Mind's container must have no `GELDAR_TELEMETRY_URL` set. The grep list is not written yet; the packet that adds the test must name it (UNVERIFIED that a repo test covers this today).
7. **Abort and error paths.** Expired or wrong token: 401, no action. Goto to an unreachable block: an error text, no hang. Mind stops mid-call: the Body does not keep moving (UNVERIFIED behaviour, to be observed).
8. **Cleanup.** Revoke the test token; stop the stack with `down` (removes volumes), per the scratch runbook.

Rehearsal without a human client: the P0 golem script joins as a stand-in for the owner's client. Run steps 1 to 3 and 6 to 8 from a script, with the MCP calls made by the same client the Mind uses, before the owner is present. Keep a clean journal for each live case (empty journal at start), and set up the world (spawn, clear area) before the Mind starts.
