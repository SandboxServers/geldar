# C7-14b: owner admin verbs in the operator wrappers

Scope: expose the existing `tools/mcp-tokens owner admin set|unset|list` (`tools/mcp-tokens/src/owner-admin.ts`) as the verb
`owner-admin` in `tools/admin/admin.sh` and `deploy/colo-admin.sh`, the same pattern as the `player-flags` verb added in C7-14.
Make `owner-add` idempotent. Add deploy test coverage for both verbs, and for the `player-flags` verb (the carry-forward from C7-14).
No SQL and no migration: the flag is `mcp_owners.is_admin` (0025), written only by `owner-admin.ts`.

Surfaces: `deploy/colo-admin.sh owner-admin set|unset|list <owner-id>`, `tools/admin/admin.sh owner-admin set|unset|list <owner-id>`.

Rules:
- `set` runs `owner admin list` first. If the owner is already an admin, `set` exits 0 and writes no `admin_set` audit row, so a re-run
  is a no-op. Otherwise it runs the UPDATE and writes one audit row.
- `unset` and `list` follow the same pattern. `unset` on a non-admin owner is a no-op, not an error.
- A missing owner (`no owner <id>`) exits non-zero, writes no audit row, and changes nothing.
- `owner-add <id>` becomes idempotent: `ON CONFLICT DO NOTHING` or an `owner exists` pre-check. A second run reports `exists`,
  exits 0, and changes nothing. Pick one; the test asserts the report and the unchanged row either way.
- Operator-created owners have no identity and cannot sign in (0011 F12). `owner-add` says so in its output. It does not create an
  identity, and the register role cannot attach one to an existing identity-less owner.

First admin (for `docs/runbooks/mcp-tokens.md`, a short "first admin" section written in the runbook step of this card):
- A first admin who can use the register UI exists only after a human's first Microsoft sign-in. That sign-in creates the owner
  through `register_create_owner`. Then the operator runs `owner-admin set <id>` on that owner id.
- An operator-created owner (from `owner-add`) has no identity and cannot sign in. It is not a first admin.
- The kill switch stays `true` until the owner opens sign-up (C7-11). Nothing in this card changes it.
- Roster seed (`roster seed`) runs only with the owner's go-ahead, passed as the operator input. It is not run by this card.
- Names only in the runbook. No values, addresses or account names.

Tests (each fails on revert):
- `owner-add` twice: the second run reports `exists`, exits 0, and the row is unchanged. Revert: restore the plain INSERT; the second run
  fails on the primary key. Error path: a database error other than the conflict still exits non-zero.
- `owner-admin set` on a non-admin owner writes one `admin_set` row and sets the flag. Revert: drop the `owner admin list` pre-check; the
  second `set` writes a second row (test: `set` twice, count the audit rows, expect 1).
- `owner-admin set` on an already-admin owner exits 0 and writes no row. Revert: the same as above.
- `owner-admin set|unset` on a missing owner exits non-zero with `no owner <id>`, writes no audit row, and changes nothing. Revert: swallow
  the UPDATE error; the test fails.
- `owner-admin unset` on a non-admin owner is a no-op with exit 0. `list` prints the admin owners and changes nothing.
- `deploy/test/` (fake `colo-admin` and `admin.sh` dependencies on PATH that record calls): both scripts route `owner-admin set|unset|list`
  and `owner-add` and `player-flags` to the CLI with the arguments unchanged. A bad verb or missing owner id exits non-zero before any call.
  Revert: remove the `owner-admin` case from one script; the test fails for that script.
- `deploy/test/` for `set`: the recorded calls show `owner admin list` before `owner admin set`, and none for a second `set` when the list
  already shows the owner as admin.
