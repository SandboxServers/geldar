# C3-04s worknote: DB roster slice for self-registered players

Card: C3-04s (docs/analysis/phase1/packets/c7b-packets.md). Branch `phase1/c3-04s-db-roster`. Migration 0024 (`mcp_roster`). Decision 0108 (Proposed).

## What changed

- `sql/0024_mcp_roster.sql`: `mcp_roster` with `player_name` primary key, `owner_id` references `mcp_owners`, `max_agents` INT 1 to 4 default 1, `created_at`. `player_name` is stored lower-cased (a CHECK `player_name = lower(player_name)` refuses any other case), and the unique index `mcp_roster_name_lower` on `lower(player_name)` keeps one row per name across owners. The CLI, the seed and `checkRosterStart` all lower-case the name; the seed's conflict clause has no target, so any unique violation skips the row.
- `sql/test/check-schema-mcp-roster.sql`: the shape, the default, the 0 and 5 refusals, the orphan refusal and the duplicate refusal. Each probe rolls back. Added to the psql line in `.github/workflows/ci.yml` (orchestrator-authorised one-line edit).
- `tools/mcp-tokens/src/roster.ts` (new): `addRosterName`, `removeRosterName`, `listRoster`, `seedRoster` (one transaction, rolls back on failure), `checkRosterStart` (row lock with `FOR UPDATE`, owner match, count of non-retired agents against `max_agents`).
- `tools/mcp-tokens/src/players.ts`: `addPlayer` calls `checkRosterStart` after the owner lookup and before the owner cap count, inside the start's transaction.
- `tools/mcp-tokens/src/cli.ts`: the `roster add|remove|list|seed` command and its usage lines.
- Tests: `roster.test.ts`, `roster-cli.test.ts`, `players.test.ts` (roster describe block and the fixture's roster and `display_name` handling).

## Deviations from the card

- `roster seed --from <file>` reads a shard-style file (`sovereign.players` list with `name`). `shards/colo.yaml` has no `sovereign.players`, so the seed is run against a file that has one. Accepted at the first coder's stage.
- The roster key is the Minecraft name, not the player id. Decision 0108 records this.
- The start check is in `tools/mcp-tokens/src/players.ts` (the start path the CLI uses). `threshold/mcp/src/` is unchanged; the card allowed a change there only where a sovereign start reads the roster, and no such read was found in that package by this slice.
- The card's C1-08 dependency (owner cap read from the yaml) was not verified in this slice. The cap used is `mcp_owners.player_cap` and trigger 0006, both unchanged.
- The ROSTER_LIMIT count uses the Minecraft name (`display_name`), not the owner: two agents of one name, for different owners, cannot happen because the name has one owner row.
- Enforcement scope (review fix B, orchestrator ruling option a): the roster is enforced at `player add` (the operator CLI) and by the supervisor's start path for the owner of the name (C7-03a, `supervisor/src/service.ts`). The golem body start path still reads `sovereign.players` from the shard file and is not gated by the roster. `max_agents` is enforced by `player add` only; the supervisor runs one body per roster name. The earlier claim that the shard file is no longer read at start time was false and is struck (decision 0108).
