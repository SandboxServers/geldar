# C7-09 worknote (account deletion)

## C7-09a (built, delete half)

Decision 0171 says what is removed and what stays. This packet implements the delete half.

### What 0171 permits, and what it does not

- Permits: removing the identity (unless banned), the owner row, players, tokens, owner keys, consents, the owner links
  on rows that carry one, and the living lives (their journal, thoughts, sleep marks and budget). Permits stopping
  bodies first, and writing one audit row keyed by an erasure id.
- Keeps: dead lives' public thoughts, events and death records, with no owner link. Audit rows (append-only).
  A tombstone (hash and ban) for a banned identity.
- Does not permit deleting audit rows, or joining world history to an owner. It does not decide the events open point:
  events of a life that was alive at deletion stay in this build, pending the owner's ruling.
- It does not say how the append-only triggers are bypassed. That is an implementation choice made here (below).

### Append-only triggers

`mcp_journal` and `thoughts` carry BEFORE UPDATE OR DELETE triggers (0007). Erasure is the one path that removes
rows from them. `register_account_delete` runs `ALTER TABLE ... DISABLE TRIGGER` on both, does the deletes, and runs
`ENABLE TRIGGER` again, all in the function's transaction. Why this and not a session flag: a session setting such as
`geldar.erasure` read by the trigger could be set by any session on the same role, so it weakens the guard for every
caller. DISABLE TRIGGER needs the table owner, is visible only inside this transaction (DDL is transactional, so a
failure rolls the disable back), and the check file tests the rollback. Other sessions still see the triggers enabled.

### Skin tables

0039 does not reference the skin tables. C7-13a must add skin_uploads (held and applied uploads, rows and PNG data) to
`register_account_delete`, and the operator removes the `geldar-skins` key as the runbook says.

### Export

Export is C7-09b and is not built here.

### Route

`POST /api/v1/account/delete` (threshold/register/src/api/account-data-delete.ts). Cookie session only, CSRF through
the router. Bearer owner keys are refused by the router (401). Order: the typed phrase; the owner (missing or banned is
401); every non-retired player's body stopped through the retire path's stop (a failure is 503 and nothing is erased);
then the erase. A second delete is a 204 no-op. Cookies are cleared on 204 (the erase removes the register sessions).

Banned owner: refused 401 (the same answer as a banned sign-in is refused), so a banned person cannot delete a
tombstone away.

### Not done in C7-09a

- The HTML typed-phrase page under the account page is not written yet.
- The route is not mounted: it needs the body deps from the NATS wiring (nats-body.ts) and the cookie-clear headers
  from account.ts wired in main.ts. The store method (PgStore.eraseAccount) exists.
- The SQL check block for the forced failure was not run on a scratch Postgres in this session.
- The audit row uses a random erasure id, not a salted hash of the owner id as 0171 point 3 suggests. This is stronger
  (no link at all), so it is a deliberate deviation; the owner may still prefer the salted hash.

## C7-09a review fix, pass 1 (in progress)

Review notes: `.claude/reports/c7/review-09a-1.md`. Status: built; review fix in progress; migration 0039.

### Decisions recorded

- F7 ACCEPTED. Deleting an account and signing up again with the same Microsoft account resets the lifetime player
  creation cap (R36, 10), the start credits (240) and the supervisor per-owner and per-name start counters. The owner id
  is derived from the identity hash, so the new owner is the same owner id, but nothing of the old use survives the
  erase. Anyone can already get fresh quotas with a new Microsoft account, so the reset adds no new capacity. Decision
  0171 is not edited.
- One service, two callers. The account page action (`runAccountDelete` in `account-delete-page.ts`) and the API route
  (`api/account-data-delete.ts`) both call `deleteAccountData`. The page and the API therefore share the order: the
  owner check, the body slot, the stop of every non-retired body, then the erase. The cookie clear comes from
  `signOutCookies()` through `accountDeleteWiring` (`account-delete-wiring.ts`), which main.ts uses.
- Banned owner: refused 401, the same answer as a banned sign-in. A tombstone (identity row with owner NULL) is refused
  the same way; `PgStore.findOwner` returns `{ownerId: '', banned: true}` for a NULL owner and never the string `'null'`.
  An unban cannot turn a tombstone into a sign-in (the identity hash is the primary key, so no fresh sign-up either).
- Route: `/account/delete` takes no player suffix. `/account/delete/ag-x/retire` is not the delete; a POST to it is 405
  and erases nothing.
- Stop name: a player whose display name fails the Body login rule (`LOGIN_NAME`, the retire route's check) is not sent
  to the supervisor; the erase still runs, because no supervisor body can carry that name.

### Open (not decided here)

- F5: a living life's `agents` row is left alive (no owner, public flags unchanged). Owner's ruling needed.
- F10 residual races and the tombstone's `provider` and `created_at` columns (see the runbook).
- The audit actor is a random erasure id, not a salted hash (a deliberate deviation, above).
- F1 and F2 (SQL check coverage, the table-lock bound) are handled in the SQL part of this branch, not in this note.
