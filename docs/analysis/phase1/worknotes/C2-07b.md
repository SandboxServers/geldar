# C2-07b: public sites into the shared Caddy (script and tests)

Split of card C2-07 by ruling R19. The desktop compose steps are C2-07a. This packet delivers `deploy/colo-public.sh`,
`deploy/test/colo-public.test.ts` and the "Public sites (C2)" section of `deploy/README.md`. Nothing was run on a node.

## Design

- Caddy substitutes `{$VAR}` from its own environment, which cannot change without a restart. `install` therefore
  renders the placeholders with sed from a root-only env file into `$GELDAR_CADDY_CONFIG_DIR/geldar/`. The directory
  holds the live file of each site at the top level (the `import` glob matches only these) and a `store/` subdirectory
  with the live and `-off` copies, so `on` and `off` are copies from `store/` with no second render.
- The Caddyfile is a single-file bind mount. It is written in place (`cat >`, `cp`), never replaced with `mv`, so the
  inode stays the same.
- Checks before any change: required env vars, host name shape, each upstream `127.0.0.1:<port>`, no `{$` left.
- The only docker calls are `exec <container> caddy validate|reload --config /etc/caddy/Caddyfile` (asserted in the test).

## For the live session (C2-07 session 2)

Run the dry run first, read the printed plan, then `install`. Keep the backup path the script prints. Rollback is
`remove`; the manual rollback is to copy the `.bak-geldar-*` file over the Caddyfile and reload.

## Known limits

- A second `install` over an existing directory that then fails validate removes the directory (the spec says so); the
  running Caddy keeps its loaded config because reload is not reached.
- The env file's mode is not checked by the script.
