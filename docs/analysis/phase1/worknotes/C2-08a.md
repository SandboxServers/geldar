# C2-08a worknote: identities table and the register role

Migration 0008 adds `mcp_identities` (no email, raw id or token column) and the NOLOGIN role `geldar_register`.

Differences from the card, found by running the tests as the role:

- `UPDATE (display)` on `mcp_owners`: the 0006 owner-cap trigger does `SELECT ... FOR UPDATE` on the owner row as the inserting role, which needs UPDATE on some column. `display` is harmless; `player_cap` is not writable by the role.
- `INSERT` on `mcp_budget`: `addPlayer` writes the first budget row in the same transaction.
- `SELECT` on `mcp_tokens` is column-level (everything but `token_hash`), so a revoke can use a WHERE.
- `agents`: INSERT on the 12 columns `addPlayer` writes; SELECT on six identifying columns, never `personality_seed`.

Retiring a player (decision 0135 item 4, card C2-08b step 6): 0008 also grants `UPDATE (status)` on `mcp_players` and nothing else on that table. The tests show the role can set `status = 'retired'` and cannot UPDATE `owner_id`, `life_id` or `player_id`. Revert-check: with the grant commented out, the retire step fails with "permission denied for table mcp_players". The open point is closed.

Tests are in `sql/test/check-schema.sql` (CI already runs it), as `SET LOCAL ROLE geldar_register`. Revert-checks: granting SELECT on thoughts fails "cannot read thoughts"; granting UPDATE (token_hash) fails the token_hash probe.
