# C7-03c2 worknote: helper install script and node runbook

Status: built on `phase1/c7-03c2`. The node steps are geldar-93's, in `docs/runbooks/body-helper-node-steps.md`.
Nothing has run on the node.

## What is in the packet

- `deploy/install-body-helper.sh`: dry run by default (`APPLY=0`); only `--apply` changes anything. It
  writes the unit, creates the two secret files if missing (never overwrites, never prints), and runs
  the `geldar_helper` password step through `tools/migrate`. It never touches `nats-auth.conf`.
- `tools/migrate`: `geldar_helper` and `geldar_supervisor` are in `PASSWORD_ROLES`. `--set-role-password`
  logs in with the file's password first and runs `ALTER ROLE` only when that login fails. The login
  probe (`probeLogin`) returns false only for SQLSTATE 28P01 or 28000 and rethrows every other error, so
  an unreachable database never leads to an `ALTER ROLE`. It is tested with a fake client
  (`tools/migrate/src/login-probe.test.ts`).
- `deploy/test/install-body-helper.test.ts`: script tests with recording fakes, and the runbook checks.
- `tools/repo-checks/src/nats-auth-runbook.test.ts`: the runbook's subject list against the generator
  (`geldar.ps1`, the `helper`, `supervisor`, `body` and `paper` lines). It fails on a `helper.body.*` wildcard.

## Decisions

1. The unit is root-owned by design (decision 0260). The SCRIPT writes the unit file; the helper never
   writes units. The reason for root is the Docker socket: the helper must connect to it, and a non-root
   unit would need the docker group, which is root-equivalent. The hardening that makes root acceptable:
   `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, and
   `ReadWritePaths` limited to the Docker socket.
2. The helper's NATS subscribe list is exactly four subjects, with no wildcard:
   `geldar.<shard>.helper.body.start`, `.stop`, `.status` and `.logtail`. Its publish is `_INBOX.>` only.
   The generator writes the same four (the `helper` line in `geldar.ps1`). An earlier draft used
   `geldar.<shard>.helper.body.*`; that wildcard grants any future or forged `helper.body.x` and is gone.
3. The card's register contradiction is resolved as "no new permission for register". The card's
   goal 3 asked for a `ctl.body.*` publish permission for `register`. The brief for this packet settles
   it: the register user is UNCHANGED, so it cannot reach the helper subjects.
4. The status probe in runbook step 4 is sent as the `supervisor` user, not `register`. The supervisor is
   the only user with publish on `status`. The card's verify line named `register`, and that line is
   superseded by this decision.
5. The supervisor entry: the runbook edits the existing `supervisor` entry if it is present. On the Colo
   node it is absent today, so the runbook adds it as a new user (its own owner go, and
   `nats-supervisor.txt` mode 0600). Its publish is `_INBOX.>` and the four helper subjects; its subscribe
   is `geldar.<shard>.ctl.body.>` and `_INBOX.>`. The masked diff masks only the value after a password,
   token, nkey or bcrypt key, so the permission lines stay visible.
6. `body` and `paper` each get a PubDeny of `geldar.<shard>.helper.body.>`. It widens live lines, so it
   has its own owner go. Without it, Paper (which publishes `geldar.<shard>.>`) could publish a helper
   start or stop.
7. Single source for the helper's NATS password: the install script creates `/etc/geldar/secrets/nats-helper.txt`
   (mode 0600). The helper's env points at that file, and the NATS conf entry for `helper` takes the same
   value by a script that reads the file. Nothing else holds a copy. The Postgres password for
   `geldar_helper` is a separate file (`helper-postgres.txt`).
8. The NATS changes follow `docs/runbooks/nats-auth-inplace.md` (staging in a 0700 directory, validation
   in the container, sha256 of the backup, the `http:` line check, the `Reloaded:` lines, the connection
   count). The runbook adds only the helper lines. It does not run `nats-server` on the host.
9. Order: the install script runs before the NATS conf change, because it creates the file the conf reads.

## Open for geldar-93

- How the helper build reaches the node. The script expects `/opt/geldar/body-helper/dist/main.js` and enables
  nothing until that file exists. Decide a pinned artifact or an env path before step 2.
- The node has no Node (geldar-worldops, node5). The unit's `ExecStart` and the password step's migrate call
  need a pinned node binary under `/opt/geldar`. That is card C7-03c5. `/opt/geldar` does not exist yet.
- The PG* variables for the password step: `sudo` drops them, and this runbook does not use `sudo -E`.
  geldar-93 decides how they reach the run. `PGDATABASE` is required.
- The `supervisor` NATS password file (`nats-supervisor.txt`) is created by step 0 of
  `nats-auth-inplace.md`, not by C7-03c2.
- The NATS client used for the step 4 status probe.
- The script's NATS password file name must be `nats-helper.txt` (decision 7). Check it against the script
  before the node run; the runbook names the ruling.
