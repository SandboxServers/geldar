## Rate rules (in migration 0067)

SQL tests in `sql/test/check-schema-skin-rules.sql`. Rulings from decision 0172:

- The daily cap (3 uploads a day) is per agent, as 0172 point 2 says. The reject wait (1 hour) is per agent.
  One pending upload per agent. The lock (point 5) is per owner.
- The lock: 3 rejects of the owner decided within 30 days of each other, not cleared. It does not lapse with time.
  It holds until the operator clears it.
- Operator clear, one statement, run as the table owner role `geldar` (no new role). It releases every uncleared reject
  of the owner, so the next 3 rejects lock again:

  `UPDATE skin_uploads SET lock_cleared_at = now() WHERE owner_id = '<owner id>' AND status = 'rejected' AND lock_cleared_at IS NULL;`

- Admin owners (0170) are exempt from the wait, the lock and the daily cap, and from nothing else.
- The audit actor of `skin.upload` is the hashed owner id (`left(encode(sha256(convert_to(owner, 'UTF8')), 'hex'), 16)`),
  as the other owner actions; the detail is the empty string.
- Errors name no owner id and no PNG bytes; the PNG and the size are checked in the function before the table's CHECK.

The lock count reads the `skin_uploads_owner_created` index (owner_id, created_at). The daily count is per agent
(player_id) and has no index of its own yet; the table is small, and a per-agent index is a follow-up if the count
shows in plans.

### B. Sign-up open (after the switch is released)

Collect the values first:
- `<cookie>`: the value of the `__Host-gr_session` cookie for the register host, from the browser's storage panel,
  in a session signed in as `<owner_id>`, who owns `<player>`.
- `<csrf>`: the `X-CSRF-Token` header of any write the account page sends (copy it from the browser's network panel).
- `skin.png`: save this script outside the repo as `make-skin.mjs` and run `node make-skin.mjs skin.png` (Node 22.2 or
  later, for `zlib.crc32`). It writes a valid 64x64 RGB PNG.

```js
import { crc32, deflateSync } from 'node:zlib';
import { writeFileSync } from 'node:fs';
const chunk = (type, data) => {
  const body = Buffer.concat([Buffer.from(type, 'ascii'), data]);
  const out = Buffer.alloc(12 + data.length);
  out.writeUInt32BE(data.length, 0);
  body.copy(out, 4);
  out.writeUInt32BE(crc32(body), 8 + data.length);
  return out;
};
const ihdr = Buffer.alloc(13);
ihdr.writeUInt32BE(64, 0);
ihdr.writeUInt32BE(64, 4);
ihdr[8] = 8;
ihdr[9] = 2;
const pixels = Buffer.alloc(64 * (1 + 64 * 3));
writeFileSync(process.argv[2], Buffer.concat([Buffer.from('89504e470d0a1a0a', 'hex'), chunk('IHDR', ihdr), chunk('IDAT', deflateSync(pixels)), chunk('IEND', Buffer.alloc(0))]));
```

For the rejected file, change the height argument `ihdr.writeUInt32BE(64, 4)` to `32`, run it again as `skin-32.png`.
For the oversize file, make any 32769-byte file (for example `head -c 32769 /dev/zero > big.bin`).

Requests, with `BASE=https://<host>/register/api/v1/agents/<player>/skin`:
1. Valid upload: `curl -si -X POST "$BASE" -H 'Content-Type: image/png' -H 'X-CSRF-Token: <csrf>' -b '__Host-gr_session=<cookie>' --data-binary @skin.png`
   expect `HTTP/1.1 202` and the body `{"uploadId":N,"status":"pending"}`.
2. Status: `curl -si "$BASE" -b '__Host-gr_session=<cookie>'` expect `200` with `"status":"pending"`.
3. Same valid file again with the same cookie and CSRF: expect `409` (a pending upload exists).
4. Bearer key: `curl -si -X POST "$BASE" -H 'Content-Type: image/png' -H 'Authorization: Bearer <key>' --data-binary @skin.png`
   expect `401` (cookie-only route).
5. Oversize: the 32769-byte file with the cookie and CSRF: expect `422` with the detail `larger than 32 KiB`.
6. Rejected file: `skin-32.png` with the cookie and CSRF: expect `422` with the detail ending `bad_size`. This one is
   refused by the validator and never reaches the database.
