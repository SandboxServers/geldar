# P1-C1-04: Colo deploy tooling (worknote)

Packet: `docs/analysis/phase1/packets/c1-packets.md`, card P1-C1-04. Decision: `docs/decisions/0084-colo-deploy-by-pull-with-a-project-scoped-script.md` (Proposed).
Branch: `phase1/c1-04-deploy`. Status of the packet: B (the build and its tests). Running on the node is an owner item (decision 0130).

## What was built

- `deploy/common.sh`: shared checks, sourced by the scripts. It holds the refusals: docker and compose v2, the daemon,
  free disk, the secret files (presence, size, mode 0600 or 0400; contents never read), the release manifest (digest
  references only), the merged-config checks (no published 25565 or 25566, every image digest-pinned, no service built
  without an image), and the BlueMap jar (https only, sha256 against the lock). Every compose call is `docker compose -p geldar-colo`.
- `deploy/colo-up.sh`: the deploy. Checks, then the merged-config validation, then the BlueMap fetch, then the release
  record, then `pull` and `up -d --wait`. Never removes a volume.
- `deploy/colo-rollback.sh`: re-applies the recorded previous release with `up -d --wait --pull never`; swaps the two records.
- `deploy/colo-down.sh`: `stop` only. `deploy/colo-status.sh`: read-only, containers found by the compose project label.
- `deploy/gen-secrets.sh`: creates the missing secret files from `/dev/urandom`, in a 0700 directory with `umask 077`.
  Never overwrites a file, never prints a value.
- `deploy/compose.secrets.yml`: an overlay that points the four secret names at the node's secrets directory.
- `deploy/release.env.example`: the release manifest template (placeholder digests only).
- `deploy/README.md`: the runbook (first-deploy order, refusals, runner or SSH, Caddy rule, stop conditions, rollback, not covered, owner actions).
- `deploy/test/colo-deploy.test.ts` (Vitest): the scripts run with a recording fake `docker` on the PATH, and with fixture
  files under a temp directory. No test runs real docker or touches a real project, and no test writes under `/etc`.
- `compose/colo.yml`: one edit (see "The eventsink blocker").
- `tools/repo-checks/src/colo-services.test.ts`: the eventsink image assertion and the every-service-has-an-image test.

## The eventsink blocker

On the merged config (`compose/colo.yml` with `deploy/compose.secrets.yml`), `eventsink` had `build:` and no `image:`.
The build-only guard in `check_merged_config` refused every deploy. The fix is one line in `compose/colo.yml`
(`image: ${GELDAR_EVENTSINK_IMAGE:-geldar-eventsink:c1}`, the same pattern as `golem-body` and `animus`), a digest-shaped
placeholder in `deploy/release.env.example`, and the assertion `every service in the colo file has an image key` in
`colo-services.test.ts`.

Revert-check: the image line was removed from `compose/colo.yml`. `colo-services.test.ts` then failed two assertions
(the eventsink image default, and `eventsink: expected ... to have property "image"`). The file was restored from a
backup; `git diff --stat` then showed only the added line. Services in the merged config with `build:`: `animus`,
`eventsink`, `golem-body`. All three have `image:`.

## Deviations from the card

- The card's `deploy/bin/` and `deploy/env/` paths were not used; the scripts are in `deploy/`. The card's may-edit
  block was rewritten to the built layout (commit `docs: align the P1-C1-04 card with the implemented deploy layout`).
- The mode assertion is skipped on win32. NTFS reports 0666 for every file, so a mode test there would only test the
  platform. `umask 077` is asserted on every platform, and the mode refusal runs wherever the tests run on Linux.
- `docker stats` has no label filter. The resource sample in `colo-status.sh` takes its container ids from the
  label-filtered `docker ps`, and passes only those ids to `stats`.
- The card's no-secrets scan (high-entropy strings, `PASSWORD=` lines over `deploy/` and `compose/colo.yml`) is not built.
  The sentinel checks cover the part that matters for this packet: no secret value appears in script output, and the
  scripts never read a secret file's contents. The repository-wide scan is a follow-up.
- `.gitignore` is not changed. The node's secret files and release manifest live outside the repository.
- `eventsink` got its image line in `compose/colo.yml` (C1-02's file, one edit). The release template's placeholder for
  it is a digest, not an empty value: an empty `*_IMAGE=` line fails the manifest's digest check.
- The card names the worknote `docs/analysis/phase1/worknotes/C1-04.md`. This file is `P1-C1-04.md`, the name the other
  worknotes use (`P1-C1-03.md` and the rest).
- The card (item 5 of the steps) says there is no `deploy/README.md` in this packet. The runbook `deploy/README.md` was
  added in this packet anyway, and the card's wording needs to be aligned at the ops merge.

## Follow-ups

1. A shell equivalent of the NATS auth generation. Today it is `./geldar.ps1 shard nats-auth` on the desktop, and the
   secrets set is copied to the node by hand.
2. An image publish workflow for `geldar-body`, `geldar-mind` and `geldar-eventsink`. Until one exists, a release cannot name a published digest for them.
3. `compose/nats-auth.yml` is not wired into the node's deploy.
4. `Set-OwnerOnlyAcl` in `geldar.ps1` returns early off Windows, so the `shard secrets` files keep default permissions on Linux. The deploy scripts check the mode (0600 or 0400), so a file made by `shard secrets` on Linux can fail the mode check until its mode is set by hand.
5. The repository-wide secret scan (see the deviations).

## Owner and ops checklist for C1-10

Read-only first, then the deploy. Stop at the first failure.

1. Copy the secrets set to the node's secrets directory, or run `deploy/gen-secrets.sh` there. Confirm each file's mode is 0600 or 0400 and the directory is 0700 and root-only. Do not paste a value into a log or a chat.
2. Put the release manifest at `/etc/geldar-colo/release.env`, mode 0600, with digests for `GELDAR_BODY_IMAGE`, `GELDAR_MIND_IMAGE` and `GELDAR_EVENTSINK_IMAGE`. Never a tag or `latest`.
3. Run `DEPLOY_DRY_RUN=1 deploy/colo-up.sh`. Read the plan. The BlueMap jar is downloaded and checked against the lock here.
4. Run `deploy/colo-status.sh` before the real deploy. Note what runs.
5. Run `deploy/colo-up.sh`. Stop on any refusal, on a BlueMap sha256 mismatch, or on `up -d --wait` failing.
6. Run `deploy/colo-status.sh` after. Every service should be healthy, and no 25565 or 25566 is published.
7. Caddy: never restart the shared Caddy. Reload only, and only C2's site snippets.
8. Owner action: accept BlueMap's Mojang asset download in the deployed `core.conf` only.
9. Rollback, if needed: `deploy/colo-rollback.sh`. It re-applies the previous release with no pull. It does not undo data changes.
