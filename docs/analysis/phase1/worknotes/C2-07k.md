# C2-07k: whitelist the Colo house Body before it joins

Problem: Paper runs with `white-list` and `enforce-whitelist` on and an empty `whitelist.json`. Velocity admits `ag_colo_01`,
then Paper kicks it ("You are not whitelisted"), and golem treats that as a permanent refusal.

Prior art: decision 0040 item 5 says Golem whitelists its bots over RCON. The players host does it per life
(`golem/src/players/whitelist.ts`, a fresh RCON connection per admission, closed after). Nothing did it for the house Body.

## Choice: (b), the admin one-shot, not golem-body

- The colo Body deliberately holds no RCON (compose/colo.yml comment; threat model rule 9). Option (a) would mount the rcon
  secret into the long-running, model-adjacent Body container.
- The admin container is a one-shot that already runs in `colo-up.sh` before the full `up`. It gains the rcon secret for the
  lifetime of one run, so the secret is in Paper, the players host (existing) and the one-shot only.
- It reuses `admitLifeOverRcon` (`admissionOnly` refuses any command but `whitelist add <that name>`), `RconClient` and
  `TestControl.whitelistAdd`, which checks the reply ("Added" or "already whitelisted").

## Shape

- `golem/src/whitelist-house-body.ts`: reads `GELDAR_SHARD_FILE` (the mounted colo shard file, `shards/colo-mind.yaml`) and
  takes `mind.agent.username`, the life id golem-body connects as, validated as `ag_` plus up to 12 of `[a-z0-9_]`.
  `shards/colo.yaml` (the budget file) holds no body names, so the name is derived the way the Body derives it. Nothing else
  is whitelisted; no human name is read or accepted.
- Subcommand `whitelist-house-body` in `tools/admin/admin.sh` and `deploy/colo-admin.sh`; the admin service gets the rcon
  secret and `GELDAR_RCON_HOST=paper` (in-network opt-in, decision 0131).
- Idempotent: `whitelist add` of a listed name replies "already whitelisted", which passes.

## Ordering

`colo-up.sh`: postgres and nats, migrations, skins bucket, then `up -d --wait paper` (waits for Paper's healthcheck),
then `whitelist-house-body`, then the full `up -d --wait` that starts golem-body. No retry loop was added, so there is no
cap to test: a failed whitelist step fails the deploy (`set -e`) before golem-body starts, and a test pins that.

## Tests

- `golem/src/whitelist-house-body.test.ts`: the name from the real shard file, refusals, one `whitelist add`, repeatable.
- `deploy/test/colo-up-order.test.ts`: paper up, then whitelist, then full up; failed whitelist stops before full up.
  Both ordering tests fail when the whitelist line is removed from `colo-up.sh` (checked).
