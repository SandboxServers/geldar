# C7-02a worknote: player token lifecycle

Decision 0170 point 1. Migration `sql/0032_token_lifecycle.sql` (ruled in by the orchestrator; 0032 reserved for this packet).

## What changed

- `register_mint_token` (0032 replaces 0010): lifetime 90 days, was 30. Still revokes older tokens at once on a fresh mint.
- `register_renew_token(identity, player, token_id, token_hash, grace_until)`: rotates. The new token keeps the player id and lives 90 days. Each older live token ends at the earliest of its own expiry, `grace_until` and 10 minutes 1 second from now. The grace is an expiry, not a revoke, so the mcp check (`expires_at > now()`) reads it unchanged. The database caps the grace, so a caller cannot extend it.
- `register_revoke_tokens(identity, player)`: revoke-only, no replacement. Returns the number of live tokens ended.
- `register_token_info(identity, player)`: the newest live token's expiry and last use, for the account page.
- All four are SECURITY DEFINER, pinned search_path, owner-scoped by the identity hash, and refuse an unknown or banned identity and a foreign player with 42501. The register role gets EXECUTE only.

## Grace boundary

`graceEndsAt(rotatedAt)` is `rotatedAt + 10 minutes + 1 second`. The old token is usable at exactly 10:00 and refused at 10:01 (the card's "10 minutes and 1 s"). The one second is `GRACE_END_SLACK_MS` in `threshold/register/src/tokens-policy.ts`.

## TypeScript

- `threshold/register/src/tokens-policy.ts`: policy functions (expiry, renewal flag, grace end).
- `threshold/register/src/tokens-service.ts`: renew, revoke and account data, behind a `TokenStore` interface. Each action runs the admin check, then the window (skipped for an admin), then the database call. A renewal and a revoke write their `register_audit` row inside the same function (0032), so the row commits or rolls back with the change; the TypeScript side writes no audit row for them. Every other outcome (limited, not_found, error) is audited by the service, and a failing error-row audit does not hide the database error. The new secret is returned only after the database call succeeds.
- `threshold/register/src/pg-store.ts`: `renewToken`, `revokeTokens`, `tokenInfo` over the functions above. A 42501 from the database is a refusal.

## Not done in this packet

- No route, page or account-page wiring yet. `account.ts` and `server.ts` are untouched. The admin exemption is in the service (`windowWait`), not at the server limiter call site.
- The owner-ban refusal of every token on the mcp side (`threshold/mcp`) is not changed here. The register side refuses a banned identity in each function.
- `sql/test/check-schema-token-lifecycle.sql` is written but unrun (psql not available locally). CI runs it. It covers the owner, ban, retired-player and no-live-token refusals (42501), the 90-day mint, the 600 to 601 second old-token expiry under a one-day grace, and a failing `register_audit` insert that rolls a renewal back.

## Known gaps (ruled by the orchestrator, for C7-10 to own)

- A refused renewal or revoke raised inside SQL (42501: another owner's player, banned identity, retired player, no live token) is audited as `not_found`: `pg-store.ts` maps 42501 to a refusal and `act` writes the row. The row does not say why it was refused; that missing reason is the gap. Accepted for C7-1 fix A; C7-10 owns the reason field.
- The supervisor role must call `supervisor_is_admin` (0027), which delegates to `register_is_admin`. It must not execute `register_is_admin` directly: `check-schema.sql` asserts that `geldar_supervisor` cannot execute `register_is_admin`.
