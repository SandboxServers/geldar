## Findings

**(a) `allow_responses` is on the user block in the generator.** `Initialize-NatsAuth` in `geldar.ps1` emits `allow_responses: true` on the user object. nats-server 2.15.1 rejects it (`unknown field "allow_responses"`), so `./geldar.ps1 shard nats-auth` writes a config that does not start. It must be inside `permissions`, which is how the test's `renderConfig` writes it. Owner: C1-06c, after C1-02 merges.

**(b) The generator still emits bare `*` per-life subjects.** It also emits an `ops` user with `>` on everything, which the overlay (`compose/nats-auth.yml`) does not mount. Owner: C1-06c.

**(c) The live test proves the design, not the generated file.** The test has its own copy of the scoped subject table (`geldar.<shard>.>`, `geldar.<shard>.body.>`). The generator does not use that table. C1-06c must make the generator output this table, and add a test that renders the real generator output and starts a server with it (the same live harness).

**(d) The scoped table is wider than the old one for body and paper publish.** Body and paper now publish to any depth under their shard (`geldar.<s>.>`), not one token. Mind and mcp publish to `geldar.<s>.body.>`. Recorded in 0087 as a consequence.

**(e) KV buckets are not shard-scoped.** `geldar-life-registry`, `geldar-checkpoints`, `geldar-body-generation`, `geldar-presence`, `geldar-skins` are shared by all shards. Any user that can read `$KV.<bucket>.>` can read it across shards. The isolation test does not cover KV. Flag for the owner: the bucket names carry no shard, so a per-shard split is a design question for a later packet.

**(f) The four existing NATS tests hardcode `127.0.0.1:4222`.** That port is held by the live dev stack, so they were not run locally against it. Their first run is in CI (the `integration` job, step 5 of this packet). Expect failures there to be reported by ops.
