## What the repo-checks test proves

`tools/repo-checks/src/nats-auth.test.ts` runs the real generator (`./geldar.ps1 shard nats-auth phase0`) in a temp copy and checks its output with booleans and subject lists, never a printed password. Twelve tests:

- The generator runs; `allow_responses` is inside each `permissions`; one password file per role matches the config's password; the six role users and no `ops`; each role's publish and subscribe lists equal the 0087 table, and no `*` token.
- Compose, with `docker compose config` offline (skipped when docker is not on PATH): colo merges with `nats-auth.yml` and keeps `-js -sd /data`; phase0 merges with `mcp.yml`, `nats-auth.yml` and `nats-auth-mcp.yml`; in each merged render, every `GELDAR_NATS_PASSWORD_FILE` is the mount target of a secret on its own service.
- Static: `Initialize-NatsAuth` exists and is dispatched; every overlay (`rcon-host.yml`, `nats-auth.yml`, `nats-auth-mcp.yml`) is in the skip lists of `geldar.ps1` and `ci.yml`; the Phase 0 chain includes `nats-auth-mcp.yml`.

The live server test (`threshold/mcp/test/nats-auth.it.test.ts`) was not changed. It still holds its own copy of the table, so it proves the design, not the generated file. That gap is open; see follow-ups.

## Defect d: colo's Body secret mount (C1-02 file)

`compose/colo.yml` gave `golem-body` `GELDAR_NATS_PASSWORD_FILE=/run/secrets/nats-body.txt`, but mounted the short-form secret `nats-body` at `/run/secrets/nats-body`. The Body would start without its password. The merged config now shows the target as `nats-body.txt` (mounted at `/run/secrets/nats-body.txt`). The Mind (`animus`) reads no NATS password in colo; the other roles (paper, velocity, eventsink) already matched their `.txt` targets.

`tools/repo-checks/src/colo-services.test.ts` pinned the short form. Its assertion is changed to the long form, with a comment. That edit is outside the packet's named files, and it is necessary: any compose fix changes that assertion.

## Output leak

A first failing run of the rendered-output tests printed the throwaway test passwords once, from a failing matcher on the config text. Fixed: those assertions are booleans now, with a comment saying why. The leaked values were test values from a scratch run, not secrets, but the rule stands: never print a generated value.
