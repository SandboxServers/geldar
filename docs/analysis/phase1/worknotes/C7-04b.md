## Notes

- `register_list_owner_keys` returns no rows for a refused presenter, so the adapter returns `[]`, not `null`.
  The service treats `null` as refused. A refused list therefore reads as an empty list. Fix when the route
  is wired.

## Continuation 1 (route handlers, partial)

- Problem codes: `conflict` (409) and `invalid` (422) added to `PROBLEM_CODES`, the status and title maps, and the OpenAPI enum in `owner-api-v1.yaml` (the register test pins the two sets equal).
- Refused list: `OwnerKeyPgStore.list` reads zero rows as null (refused). The SQL cannot tell a refused presenter from an empty list by itself, but a successful list always holds the presenter's own key (the list is the owner's keys and the presenter key is one of them), so an empty result is never a successful list. No migration. Residual: a key row purged by a future retention job would read as refused; C7-10 must keep the presenter's key row or change this rule.
- Revoked-key replay bound (orchestrator ruling): no migration. The source IP limiter from C7-04a runs before the key resolve and caps the rate of replays. Carry-forward to C7-10: audit retention for `key.use` rows.
- `GET /agents` (agents-list.ts): own agents only, projected onto the Agent field list, so a stored token hash never leaves. A missing list loader is 500 internal, never an empty list.
- Gap, token routes (not built): `TokenStore` (tokens-service.ts) is keyed by `identityHash` (the browser identity). The API credential carries only `ownerId`, and `ownerId` is `reg-` plus a 24-character prefix of the identity hash (account.ts), so a Bearer key cannot reach the store. Needs a decision: token routes for cookie sessions only (the session row has the identity hash), or an owner-to-identity lookup (a definer function, which is a migration outside this packet).
- Gap, owner-key routes (not built): `owner-keys-service.ts` acts on a presented owner key (Bearer). A cookie session has no key, so the owner-key routes would be Bearer-only.
- Not built in this pass: PATCH /agents/{playerId}, POST /agents/{id}/tokens (and revoke), GET/POST/revoke /owner-keys, their tests, the black-box MCP and replay tests, the show-once and CSRF tests.

## Continuation 2 (decision 0173, C7-04b-3)

- The two gaps above are settled by decision 0173 (API v1): token rotate and revoke and all owner-key routes are cookie-session only (CSRF on writes). A Bearer owner key at those routes is 401 `unauthenticated`. Bearer keys carry `read` and `body`; `manage` is checked by the database but no Bearer route uses it in v1.
- The cookie session path is built in C7-04b-3: migration 0035 (`register_session_mint_owner_key`, `register_session_list_owner_keys`, `register_session_revoke_owner_key`, keyed by the identity hash), the adapter methods in `owner-keys-pg.ts` (a refused list raises `scope_missing`, never `[]`), and `mintOwnerKeyBySession`, `listOwnerKeysBySession`, `revokeOwnerKeyBySession` in `owner-keys-service.ts`.
- The `[]`-on-refusal residue above is closed for the session path. The Bearer path (`list` in `owner-keys-pg.ts`) keeps the zero-row rule until C7-04d.
- Route wiring (`api/tokens.ts`, `api/owner-keys.ts`, `api/agents.ts` PATCH) is not in C7-04b-3; it follows the card's credential table.
- Bearer-driven rotation and key management: candidate C7-04d (needs an owner-id keyed token SQL path and a migration).
