# C2-02b worknote: ghosts are held in spectator

Follow-up to C2-02 (decision 0092).

## Path chosen

Paper has no access to the registry `live` flag (Geldar-Core talks to NATS only to publish events). The fewest new moving parts: Velocity already holds the classification (`LoginGate.isSpectator`), so it sends one plugin message `geldar:ghost` after the backend connection is up. No new NATS subject, bucket or Paper dependency.

## Changes

- `IdentityPlugin`: registers `geldar:ghost`; `onServerPostConnect` sends it for a ghost.
- `GhostListener` (core): plugin-message receiver and listener. Forces `GameMode.SPECTATOR` on the signal, join, respawn and world change; cancels game-mode changes away from spectator; cancels `AsyncChatEvent` from a ghost (agents must not learn they are watched, 0059, 0068); forgets on quit. A failing `setGameMode` is logged, never thrown.
- `LifeRegistration.put` (golem): writes `live: true`. The death behaviour is unchanged: a dead life's key is deleted, so a dead life is unregistered, not a ghost. Spec 8.4 defines a ghost as a human spectator account, so `live: false` belongs to a future ghost writer (`geldar ghost add`), still undecided.

## Limits

- Interaction: a spectator cannot break, place or use blocks in vanilla; no extra cancel was added. The PlayerInteract path is unchanged.
- Between join and the signal (a few ticks) the ghost is in the backend's default mode. The window is not closed; closing it needs a Paper-side check on a registry cache.
- The respawn handler is not unit tested: `PlayerRespawnEvent` cannot be built without a server.
- The Velocity handler has no unit test (Player and RegisteredServer fakes are heavy); it is covered by the live lane.
- live: pending.
