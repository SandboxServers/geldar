# Kino runbook

Kino is the owner-facing 3D view of what one agent sees (decision 0075). It is OFF by default at every layer. It is a window: it sends nothing into the world, and no human acts in the world through it. The agents are never told they are watched.

Three switches, all default off:

| Layer | Setting | Off means |
|---|---|---|
| Plugin | `kino.enabled` in the Geldar-Core `config.yml` (default `false`) | the feed is killed and publishes nothing |
| Glass | `GELDAR_KINO_ENABLED` (default `0`) | no NATS connection, no `/kino/` page, no WebSocket route |
| Caddy | `GELDAR_KINO_ENABLED` in Caddy's environment (default `0`) | `/kino*` on the Glass host answers 404 |

## Enable

1. Sign-in. Kino uses the one `gk_session` cookie of the Glass host, signed in through the register service. Its Microsoft (Entra) app is set by `REGISTER_MS_CLIENT_ID` and `REGISTER_PUBLIC_URL` is the Glass origin, `https://glass.<domain>` (the same origin as `GELDAR_KINO_PUBLIC_ORIGIN`), so the redirect URI registered in the Entra app is `https://glass.<domain>/register/callback`; the Caddy `/register*` route on the Glass site serves it. The client secret is a file in the secrets directory (`GELDAR_SECRETS_DIR`), named by `REGISTER_MS_CLIENT_SECRET_FILE=/run/secrets/register-ms-secret`; the file is `register-ms-secret.txt`. `gen-secrets.sh` never creates it: create it on the node yourself (mode 0600) with the value from the Entra app. Its value is never in the repo, in an env file or in a log. Signed-in viewing is optional and off until you merge `compose/colo-kino-session.yml` after `colo-kino.yml`: it mounts the session key file `register-session-key.txt` (generated by `gen-secrets.sh`, declared once in `compose/colo.yml`) from the secrets directory (the file the register deploy reads as `REGISTER_SESSION_KEY_FILE`, at least 32 characters, the same value for both) and sets `GELDAR_GLASS_SESSION_KEY_FILE` for Glass. Without the overlay Glass runs anonymous-only: `/kino/targets` lists public-camera agents only. With it, Glass verifies the `gk_session` cookie and owners see their own agents.
2. NATS. The `kino` NATS user is made by `./geldar.ps1 shard nats-auth colo` with the others (password file `nats-kino.txt` in the secrets directory). It may subscribe to `geldar.<shard>.kino.*.feed` and publish `geldar.<shard>.kino.control`, and nothing else. Only the plugin (`paper` user) may publish the feed and subscribe to control; the `body` user may do neither (its publish allow has a deny on `geldar.<shard>.kino.>`). If you made `nats-auth.conf` before the `kino` user existed, delete it and rerun `shard nats-auth colo` (the other password files are kept) so the `kino` user and the new deny lists are in the server config (already done on the Colo). `GELDAR_KINO_NATS_USER` defaults to `kino`. Glass builds its subjects from `GELDAR_SHARD`, which `colo-kino.yml` sets to `colo`; Glass refuses to start Kino when `GELDAR_KINO_ENABLED` is on and `GELDAR_SHARD` is unset (a wrong shard shows as Publish/Subscription Violations in the NATS log). Add `-f compose/colo-kino.yml` to the compose merge for Glass; the base `colo.yml` keeps Glass free of NATS. The NATS monitor is not on the colo network: the base has none, and the `nats-auth` overlay binds it to `127.0.0.1:8222` inside the container (`http:` in the generated conf; its subsz detail would name who is watched). Regenerating `nats-auth.conf` for the monitor line is optional: the NATS healthcheck probes only the client port (4222, `nc -z`), so an older conf without the monitor stays healthy. Regenerate only to get the `kino` user or the monitor.
3. Optional metrics. Set `GELDAR_KINO_OTLP_ENDPOINT` to the SigNoz OTLP/HTTP base URL. Unset: nothing is exported. Exported: `kino.panes_open`, `kino.bytes_sent` and `kino.refusals` (label `reason` only; no agent, login or account label).
4. Set `GELDAR_KINO_PUBLIC_ORIGIN` to the full origin of the Glass host, `https://glass.<domain>` (required: the merge of `colo-kino.yml` fails without it; Compose passes it to Glass as `GELDAR_KINO_ALLOWED_ORIGINS`, and Glass refuses to start Kino with an empty list). Behind Caddy the Host Glass sees is always `localhost`, so only this list admits a browser Origin. Textures: the page loads BlueMap's `textures.json` through `https://glass.<domain>/kino/tex/` (only `/kino/tex/maps/<map>/textures.json` is proxied: Caddy strips the prefix and proxies the map upstream, GET and HEAD only, without the Cookie and Authorization request headers and without Set-Cookie in the answer; every other path under `/kino/tex/` is 404, so the map site's pages and scripts never run on the Glass origin; `deploy/colo-public.sh` renders it from `GELDAR_MAP_UPSTREAM`), so the CSP stays `connect-src 'self'`. Set the `kino-textures-url` meta tag to `/kino/tex/maps/<map>/textures.json`. Then set `GELDAR_KINO_ENABLED=1` in the Glass deploy env and in Caddy's environment, then recreate Glass (`compose up -d glass`) and publish the Glass site file: the shared Caddy has its admin API off (R39), so it is restarted once, not reloaded. Validate first with `bash deploy/caddy/validate.sh`, then run `GELDAR_PUBLIC_APPLY=restart bash deploy/colo-public.sh install glass` (the Colo env file sets it): it writes and validates the files and prints `RESTART board-proxy once to apply`. Restart `board-proxy` once yourself (`docker restart board-proxy`), or set `GELDAR_PUBLIC_RESTART_OK=1` so the script does it once and waits for the container and `caddy validate`. Without `GELDAR_REGISTER_UPSTREAM` in the env file, `/register*` and `/roster*` answer 503.
5. Set `kino.enabled: true` in the plugin `config.yml`. The plugin re-reads the file every 5 seconds; no restart is needed.
6. Open `https://glass.<domain>/kino/` while signed in.

## View window

The feed reads the loaded chunks within `kino.radius_chunks` (default 5; 1 to 8) horizontally. The vertical band tapers with distance: within 4 chunks it reads 6 sections above the agent and 1 below; beyond 4 chunks, only 2 above and 2 below the agent's height. The feed queues the sections nearest-first from the agent's own section, so the view fills outward from the agent, and it re-sorts the queue when the agent changes chunk. A section that is entirely opaque and sealed by opaque neighbours (no face open to air, cave or water) is not sent, since no camera can see it; a section next to an unloaded chunk or at the world's top or bottom is always sent. The block reads stay within 16384 per tick, so a wide window arrives over a few seconds.

## Kill switch

Any one of these stops Kino. Use the first for speed.

1. Plugin: set `kino.enabled: false`. Within 5 seconds every target gets `bye` and the feed stops.
2. Glass and Caddy: set `GELDAR_KINO_ENABLED=0` in both, recreate Glass and restart Caddy once (admin API off). Open panes are closed with `kill_switch`; the route returns 404.
3. Everything on the Glass host: load `glass-off.caddy` (`deploy/colo-public.sh off glass`).
4. Sign-in only: leave `REGISTER_KILL_SWITCH` at `true` (the default; only the exact value `false` turns it off) and recreate the register service with the Colo compose files (`up -d register`). New sign-ins stop. Steps 1 to 3 are what stop the feed itself.

To turn Kino back on, reverse the step you took. A pane that was closed does not reopen by itself; the browser must connect again.

## Audit

Pane opens, targets, mode changes and closes are recorded in `kino_audit` with a hashed login, kept 90 days (Glass purges older rows daily). If an audit write fails, the pane is closed (fail closed).

## Entry page and control path (K09)

`/kino/` is the production page (`glass/web/kino/index.html`, module `main.ts`, styles `kino.css`); `/kino/dev.html` is the mock-feed dev page. Since decision 0161 the page is a monitor wall: up to 4 monitors (Wall, Feature and Solo layouts), one active monitor that the keyboard drives, a channel guide (`T`) and a controls card (`?`). The camera mode called `follow` on the wire is shown as **Chase** (the Lakitu camera); `orbit` and `free` keep their names. The per-monitor status line is folded behind the info button and the top bar's Details button; its text and the `#status` id are unchanged. The wall a viewer leaves is kept in their browser (`localStorage`, key `kino-wall-v1`) and restored for agents the server still lists. To look at the page without a shard, run the test-only preview: `node glass/test/kino-preview/server.ts [port]` (default 8789, loopback, an invented world with three walking agents; see `glass/README.md`). The page reads `/kino/targets` (signed-in state and the agents the server lets this viewer watch; anonymous viewers get public-camera agents only), shows a sign-in link when not signed in, and ends a pane on `bye` (including `kill_switch`). Set the `kino-signin-url` and `kino-textures-url` meta tags in `index.html` per deploy (`kino-textures-url` must be the same-origin `/kino/tex/maps/<map>/textures.json`; a `?textures=` URL on another origin is blocked by the CSP).

Glass asks the plugin to read an agent over NATS on `geldar.<shard>.kino.control` (`kino-control.schema.json`): `start` for the first pane, `resync` for later panes, `refresh` every 15 s while watched, `stop` 10 s after the last pane leaves. The plugin applies these on the server thread only when `kino.enabled` is true; a target not refreshed for 45 s is stopped, so a Glass restart leaves nothing running. NATS permissions (generated in `Get-NatsUsers`, proved by `tools/repo-checks/src/nats-auth.test.ts`): Glass (`kino`) may publish `geldar.<shard>.kino.control` and subscribe `geldar.<shard>.kino.*.feed`; the plugin (`paper`) may subscribe `geldar.<shard>.kino.control` and publish the feed, and is denied publishing control. Glass reads agent ownership through the definer functions `kino_viewer` and `kino_agent_scope` (migration 0017); `geldar_glass` has no grant on `mcp_identities` or `agents.owner`.

Block ownership (decision 0165, `block-owner.schema.json`): the plugin records who placed each block the agents placed, per chunk, and answers over NATS. `geldar.<shard>.blockowner.query` is a request/reply subject the plugin subscribes to (`paper`); the reply is a `BlockOwnerReply` (at most 4096 blocks per chunk, `truncated` when there are more). `geldar.<shard>.blockowner.changed` is published by the plugin (`paper`) when one block's owner changes (`owner` null when cleared). The `body` user may query and subscribe to changed, and is denied publishing changed, so a Body cannot forge an owner. The `kino` user and every other user have no access to either subject. Blocks with no record are world-generated.
## Seeing the live site: kino-shot

`tools/kino-shot` opens a Kino page in headless Chromium (Playwright 1.64.1) and saves evidence, so you can look at the live site without a desktop browser. It is optional: nothing in `setup`, CI or `pnpm -r` runs it, the install uses `--ignore-scripts`, and the package has no postinstall. The browser is a separate download, once per machine (cached under the user-level Playwright cache, not in the repo):

```
./geldar.ps1 pnpm --filter @geldar/kino-shot browsers
$env:KINO_URL = 'https://<glass host>/kino/'   # never commit the host
./geldar.ps1 pnpm --filter @geldar/kino-shot shot -- --agent ag_jason_01 --mode follow --seconds 25
```

Options: `--url` (or `KINO_URL`; https only, http only for localhost), `--agent` (an id or the label the page shows), `--mode follow|orbit|free`, `--seconds` (default 25), `--viewport 430x900` (mobile viewport and touch UA by default), `--out` (default `.claude/kino-shots/`, gitignored, relative to where you typed the command). One run is one anonymous page load: no sign-in, no cookies or tokens stored, console text is redacted for anything token-like. Do not loop it; the site rate-limits.

Software WebGL needs the flags `--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist`; these work on Windows (the canvas renders).

Outputs: `screenshot.png` (full page), `canvas.png` (the pane canvas, composited), `status.txt` (every visible status text; the bar line stays at its first value, the pane line at the bottom of the canvas is the live one), `console.log` (console messages, page errors, failed requests, same-origin HTTP errors, 429s marked `!!!`), `network-summary.json` (counts by HTTP status and by WebSocket message `type`; no payloads). Stdout is one JSON line: `checks` (picker populated, that is the channel guide lists agents, connected, chunks, canvas rendered), pixel `fractions` of near-magenta (a missing texture) and near-black, `count429`, and `ok`. The exit code is 1 when a check fails (picker empty, not connected, no chunks, canvas mostly magenta or black), 2 on a crash.
