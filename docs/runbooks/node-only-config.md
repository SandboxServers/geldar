# Runbook: node-only configuration inventory (Colo)

Scope: what the Colo node runs or holds that the repo does not reproduce. Verified 2026-11-14/15. Input for the genesis campaign (`docs/analysis/genesis/`), which is making the world's configuration reproducible; genesis owns the fixes, this file lists the gaps.

Conventions: this file records where things live and how they were set, never their values. No secrets, addresses or account names. Repo paths are cited only where `git grep` or `git ls-files` found them on main. A row marked *(not in repo)* has no repo source.

## Reproduction order

What genesis should script first, in this order:

1. **Gamerule startup lines.** `compose/phase0.yml` has no `players_sleeping_percentage` line; add it next to the others, and keep `compose/colo.yml` line 138. Confirm the live value read-only with `gamerule players_sleeping_percentage`. This is the cheapest gap to close.
2. **Compose sync check.** Compare the node's `compose/colo.yml` with main before any deploy. Without it, items 1 and 3 drift silently.
3. **Aliases from a repo-tracked source.** Item 4 is never committed. Genesis needs a tracked source (a template or an encrypted file) that renders `aliases.json`, followed by a Glass restart.
4. **NATS auth generated-vs-live check.** Compare `nats-auth.conf` with `Get-NatsUsers` output (user list and permission lines, passwords redacted). Item 5 already drifts by 3 users (`helper`, `supervisor`, `register`) from the colo table, and deny lines.
5. **CoreProtect config template.** Item 2's config is set by hand after the first start. Genesis needs a template whose keys are confirmed against the file the plugin writes. The database (graves and placement history) is data: back it up, do not reproduce it.

Items 6 to 15 are either owner-gated (6, 9), data (10 to 12), or outside Colo (15). They need a decision, not a script.

## Docker data root for the deploy floor (DR-1, #866)

The deploy floor reads Docker's data root from the `data-root` key of `/etc/docker/daemon.json` first (an absent or unreadable file falls through), then with `docker info --format '{{.DockerRootDir}}'`, then with `sudo -n docker info --format '{{.DockerRootDir}}'`. When none answers, the deploy refuses (it does not warn). The unprivileged deploy runner account usually cannot run `docker info`, so the runner needs one of these, decided by the owner:

- A sudoers rule that lets the runner account run exactly `docker info --format {{.DockerRootDir}}` as root without a password, for example `<runner account> ALL=(root) NOPASSWD: /usr/bin/docker info --format {{.DockerRootDir}}`, placed in a file under `/etc/sudoers.d/` and checked with `visudo -c`. Node-side step, not in the repo.
- Or a `data-root` key in `/etc/docker/daemon.json` that names the data root (readable by the runner).

Without one of them the `colo-deploy.yml` inbox step fails with "cannot determine Docker's data root". No host names are recorded here.
