## Decision

1. **Humans are players on the NeoForge shard (0387).** The NeoForge human lane is reachable from the internet. Anyone with a Microsoft (Mojang) account who passes the lane's refusals may join. The shard has no server whitelist (owner, 2026-11-17, 0387).
2. **The public name is an SRV record only.** Players type the hostname and no port. The SRV record names the human port. The game port is TCP, so Caddy is not involved (Caddy serves HTTP and HTTPS). The gateway that forwards the port is owner-owned, and the owner removes it to roll back.
3. **The agent lane stays loopback-only.** The agent Velocity stays on `127.0.0.1:46565`, unchanged. Nothing on the human side reaches it: the human network carries only the human proxy, NATS and the NeoForge server.

## What is built

Merged to main as #731 (the H6 branch `phase1/nf-human-inbox`, tip 46cdf15a, which contains the H5 tip 9aa37c1f; the repo tests pin each item):

Nothing else joins it. The one published port is `${NF_HUMAN_BIND:-127.0.0.1}:${NF_HUMAN_PORT:-46566}` to container port 25565. The service is `read_only`, `cap_drop: ALL`, has `no-new-privileges`, runs as the service uid, and mounts the identity jar read-only with `create_host_path: false`. Its restart policy in the repo is `"no"` (`compose/nf-live-human.yml:108`): nothing restarts the proxy after a failed start or a host reboot. OPEN ITEM: the live `velocity-human` container was set to `unless-stopped` with `docker update` on 2026-11-18, so the live policy and the repo disagree until the reboot-policy PR flips the file (runbook 10.8).
- **Inbox prefix (H6)**: the human proxy has its own NATS inbox prefix, `GELDAR_NATS_INBOX_PREFIX: "_INBOX.human."` (`compose/nf-live-human.yml:54`, set on `velocity-human` only). The deployed conf keeps the H5 grant `_INBOX.>` (#729) until it is regenerated (gate item 2). This narrows the shared-inbox exposure, but it is account-level isolation only: the human user shares one NATS account with the others. A separate NATS account is NOT built and NOT in scope.
- **Healthcheck**: the proxy is healthy when the identity plugin's ready marker `/tmp/geldar-identity.ready` names a live process (its pid and start time, matched against `/proc`) and port 25565 accepts a connection. Interval 5 s, timeout 3 s, 3 retries, start period 20 s (`compose/nf-live-human.yml:84-93`). A plugin that never writes the marker makes `up --wait` fail after 35 s, not after 110 s. What the check proves: the plugin loaded and the port is open. - **NATS user `human`**: read-only on the two identity buckets (`geldar-life-registry` and `geldar-skins`), with its flow-control subjects. It publishes no `$KV` write and no event subject (`deploy/nats-auth-nf.ps1`, the comment at line 57 and the `human` entry of the user table). It is a separate user from `velocity`.

The orphan guard (`deploy/nf-human-lib.sh`, the velocity-human check): with `NF_HUMAN` unset or `off`, `plan`, `up`, `refresh-secrets` and `probe` REFUSE while a `velocity-human` container exists in the project, and name `human-down` and `NF_HUMAN=on` as the two ways out. `status`, `logs`, `down` and `human-down` stay allowed. The first `NF_HUMAN=on` `plan` says that it recreates `nats`, `eventsink` and `neoforge`, because their network set changes (`deploy/nf-deploy.sh`, the plan text). The validated `NF_HUMAN_BIND` and `NF_HUMAN_PORT` are exported (`deploy/nf-human-lib.sh`, the export line), so the shell value takes precedence over `compose/.env`. A failed `velocity-human` start stops only that service.

## Residual risks

Each item is an ACCEPTED RISK by the owner's acceptance of this record on 2026-11-18, unless it says otherwise. They are kept here, stated plainly, so that a reader sees what was accepted.

1. **ACCEPTED RISK. One forwarding secret is shared by three proxies.** The agent proxy, the human proxy and the NeoForge server all use the same Proxy Compatible Forge forwarding secret (`compose/velocity/velocity-nf-human.toml` line 6 says so; the agent velocity reads the same file). Whether Proxy Compatible Forge accepts a second secret was NOT verified: no artefact was available to check it. Consequence: a compromised public proxy could forge any identity, including an agent name, to the NeoForge server. Mitigations in place: Velocity is the only path to NeoForge; NeoForge publishes nothing; `nf-human` holds only `velocity-human`, `nats` and `neoforge`, so the human proxy cannot reach postgres or the event sink by name; the human proxy has no shell, runs with `cap_drop: ALL`, `read_only`, `no-new-privileges` and the service uid, and holds only a read-only NATS credential. The lane identity is not carried in modern forwarding data, so the separation between the lanes rests on the human proxy's `LoginGate` refusals alone (the review of H2, finding F6, recorded this as an accepted risk).
2. **ACCEPTED RISK. RCON reachability.** The NeoForge RCON port is reachable by name from `nf-human`, because `neoforge` is on that network. The RCON password is never mounted into `velocity-human`, so a compromised proxy holds no RCON password. Whether RCON binds only to loopback inside the NeoForge container was NOT verified.
3. **ACCEPTED RISK. Cap abuse (H1b DROPPED, rate limits left alone).** With no whitelist, anyone with a Microsoft account may join. Under the shared limit of 100 (section "Amends 0137 for the NeoForge shard"), the abuse is filling the shared limit: enough throwaway accounts to fill the 100 shared slots would also lock out every agent trying to join, because agents share that limit. There is no per-IP limit, no login rate limiting beyond Velocity's default, and no idle kick. The owner accepted this on 2026-11-18.
4. **ACCEPTED RISK; slot release OBSERVED for one join and leave (2026-11-18). Concurrency and the cap are untested.** The slot mechanism assumes that Velocity hands the same `Player` object to `LoginEvent` and to `DisconnectEvent`. On 2026-11-18 a join through the public name reserved a slot (`human slot reserved: 1/100`, 17:01:27Z) and its disconnect released it (`human slot released: 0/100`, 17:03:21Z), with no `found no slot` warning (the slot-logging PR #741, merged as a583114b; runbook section 10.8). What that shows: one human, one join, one leave, sequentially, on the live human proxy. What it does NOT show: two or more concurrent humans, the 101st-player refusal at 100, or that `DisconnectEvent` fires for every connection that ends after a login. Those stay UNVERIFIED.
5. **ACCEPTED RISK. Login rate limit is Velocity's default (H1b DROPPED).** `login-ratelimit` is not set (3000 ms per source address). If the public connections reach the proxy through a Docker userland proxy, every client may appear as the bridge gateway, and one client connecting every few seconds could lock out the others. Not verified on a node.
6. **ACCEPTED RISK. Player addresses are logged.** `enable-player-address-logging = true` writes public players' addresses to the container's JSON log (three files of 10 MB).
7. **ACCEPTED RISK. No human registry (0387 item 5(d) DROPPED).** The owner decided on 2026-11-18 that online identity is enough: the Microsoft login is the identity, and there is no human registry check. The lane's refusals (section "What is built") are the only per-login refusals. A human cannot be revoked by the lane: there is no revocation path beyond the whitelist-less lane's own refusals.
8. **ACCEPTED RISK; first joins done 2026-11-18 (the owner's account, two joins).** A plain-client join on the LAN and a join through the public name both worked (runbook 10.8). No second human has joined. Every claim about the human lane not listed in 10.8 is from renders, tests and reading, not from a running server.
9. **ACCEPTED RISK; UNVERIFIED on a live NATS. The inbox prefix (H6).** On the first join (2026-11-18) the KV watches ran under `_INBOX.human.` with no NATS violation logged, so that part is observed. Still not shown on a server: the exact permission set a push watch needs, that the server enforces `_INBOX.human.>` against an attempted violation (none was attempted), and whether the client ever publishes to an inbox. Under the stack, the healthcheck proves plugin load and an open port. Registry sync is proven only once the #726 gate is deployed on the human proxy and the first real join has happened.
10. **ACCEPTED FOR NOW (owner, 2026-11-18, "leave nats as is"): NATS cannot constrain a consumer's delivery subject (review H6, finding 4; pre-existing, NOT introduced by H6).** NATS permissions are subject-based only. They cannot constrain a consumer's `deliver_subject`, name, config or count. A compromised public proxy that holds `CONSUMER.CREATE` on the two identity KV streams could aim server-delivered registry and skin entries at any subject it can name, and could create consumers without bound. The `velocity` user holds the same grant, so this is not new, and H6 does not remove it. What H6 blocks, by reading the grant (NOT a live check): the human proxy cannot read other users' inbox traffic (its subscribe is `_INBOX.human.>` only), cannot publish into other users' inboxes, and cannot enumerate consumer names (no `CONSUMER.LIST`, `CONSUMER.NAMES` or `$JS.EVENT`). Forging flow control into the agent proxy's consumers should also be blocked, but that rests on a reading of the grant, not on a live check. The only remedy is a separate NATS account with an export and import of the KV read. That is NOT built and NOT in scope. Revisit with a separate NATS account later.
11. **ACCEPTED RISK. The human user's `_INBOX.human.>` publish grant is kept** until the first real join shows that the client never publishes to an inbox. Removing it is a follow-up (review H6, finding 5).
