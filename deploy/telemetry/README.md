## Secrets

Sudo scope for the node steps: `mkdir` and `chown` inside `/mnt/nvme/geldar-telemetry` only. Anything else (including `sudo stat`, `sudo cat`, and files in `/tmp`) must be asked for first.

Passwords are never inline. Compose mounts them as file secrets from `/mnt/nvme/geldar-telemetry/secrets/`:

- `ch_writer_password`: the writer password. Used by the migrator and the collector.
- `ch_reader_password`: the reader password. Used by the query service.

**Password format (S-E):** each password is 32 random bytes as 64 lowercase hex characters (`[0-9a-f]` only, for example `openssl rand -hex 32`). No other characters: the value is placed in a `tcp://user:password@host` URL, where `@ / : ? # %` break the parse. Each file has no trailing text; `$(cat)` strips the final newline.

**File owner and mode.** Compose ignores `uid`, `gid` and `mode` on file secrets on a non-Swarm engine `[INF]`, and this compose file does not set them. The container sees the host file's owner and mode. Create the files with the owner and mode below, then check with `ls -ln` (see item 14). The owner is numeric because the container has no name for it.

| File (host) | Read by | Runs as | Required owner:mode |
|---|---|---|---|
| `secrets/ch_writer_password` | `geldar-signoz-migrator`, `geldar-signoz-otelcol` (wrapper) | uid 10001 (image `User`) | `10001:10001` `0400` |
| `secrets/ch_reader_password` | `geldar-signoz` (wrapper) | uid 0 (root, no USER; `cap_drop: ALL`, so no DAC_OVERRIDE) | `0:0` `0400` |
| `secrets/ch-hashes.env` | the compose client, which passes it to `geldar-ch` as env (`env_file`); no container reads the file | the operator running compose | operator's own uid, `0400` |

A reader file owned by 10001 would be unreadable to `geldar-signoz` (root without DAC_OVERRIDE cannot read a 0400 file owned by another uid); a writer file owned by root would be unreadable to 10001.

### Password hashes

`clickhouse/users.d/users.xml` is well-formed and contains no hash. Each user reads its hash with `<password_sha256_hex from_env="..."/>`: `GELDAR_CH_WRITER_SHA256` (writer) and `GELDAR_CH_READER_SHA256` (reader). `geldar-ch` loads them from `/mnt/nvme/geldar-telemetry/secrets/ch-hashes.env` (compose `env_file`, not in git). Write that file on the node, mode 0400, with two lines `GELDAR_CH_WRITER_SHA256=<hex>` and `GELDAR_CH_READER_SHA256=<hex>`. Make each hex with the guarded form below, run as host root (`sudo`), which can read both 0400 secret files whatever their owner. The form stops on an empty or short password, so an unreadable file cannot produce a hash:

```
pw=$(cat /mnt/nvme/geldar-telemetry/secrets/ch_writer_password) && [ "${#pw}" -eq 64 ] && printf %s "$pw" | sha256sum | cut -d' ' -f1
```

Use the same form for `ch_reader_password`. If a command prints nothing or exits non-zero, stop and do not write that hash. The hash `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` is the SHA-256 of the empty string (what an empty password would give); if it appears in `ch-hashes.env`, delete that file and start again. Do not put the values in a command line that is saved in shell history.

- `from_env` in ClickHouse config is `[INF]`, unverified on 25.12.5. **Blocks start of geldar-ch** (a missing variable is a start failure, which fails closed).
- Residual exposure: the hash is in the container environment, so `docker inspect geldar-ch` shows it to anyone with Docker access. A sha256 of a password can be brute-forced offline. Docker access is root-equivalent on this host, so this is accepted, not removed.

### Secret wrappers (migrator, SigNoz, collector)

The DSNs are built by a short shell wrapper that reads the secret file at start (see the compose `command:` lines). The wrapper text contains `$(cat /run/secrets/...)`, not the value, so no password is in argv or in `docker inspect`. The value lives in the environment of the running process, which is readable by root and by the same uid through `/proc/<pid>/environ`. That residual exposure is accepted for this single-node host. The migrator uses the collector image (`signoz/signoz-otel-collector`, see the Pins), so its DSN is an environment variable, as the SigNoz `migrate` subcommands expect. The wrapper relies on `/bin/sh` in the image: `[UNV]` for the collector and the SigNoz image is alpine.

No secret value, token or account name is in this directory.

## Healthchecks and restarts

Compose gates start on health. `geldar-ch` waits for `geldar-ch-keeper` to be healthy. The migrator, `geldar-signoz` and `geldar-signoz-otelcol` wait for `geldar-ch` to be healthy. So a failing Keeper healthcheck stops `geldar-ch` from starting, and a failing ClickHouse healthcheck stops the migrator, SigNoz and the collector from starting. The blocked services are not restarted and do not start at all.

Nothing restarts a service because of a healthcheck: plain Docker does not act on `unhealthy`, and there is no autoheal sidecar. Restart loops (`restart: unless-stopped`) come only from a process exit, for example a ClickHouse config parse error. Those do not damage data.

    ```
    docker run --rm --net container:geldar-signoz "$BB" cat /proc/net/tcp /proc/net/tcp6
    ```

    State `02` is SYN_SENT and `01` is ESTABLISHED. Decode the remote field `RRRRRRRR:PPPP` (column 3). For IPv4 the 8 hex digits are the address with the byte order reversed (little-endian), and the port is plain big-endian hex. Recipe:

    ```
    docker run --rm --net container:geldar-signoz "$BB" sh -c 'tail -n +2 /proc/net/tcp | while read sl loc rem st rest; do case $st in 01|02) h=${rem%:*}; p=${rem#*:}; printf "state=%s remote=%d.%d.%d.%d port=%d\n" $st 0x$(echo $h|cut -c7-8) 0x$(echo $h|cut -c5-6) 0x$(echo $h|cut -c3-4) 0x$(echo $h|cut -c1-2) 0x$p;; esac; done'
    ```

    This one-liner was written for this README and has not been run; if it fails, decode by hand: split `0100007F:1F90` into byte pairs `01 00 00 7F`, reverse them to `7F 00 00 01` (127.0.0.1), and read `1F90` as 8080. For `/proc/net/tcp6` each 4-byte group is reversed separately; a mapped IPv4 address ends in `0000FFFF` plus the reversed IPv4 group. Record the port, whether the address is private (RFC1918) or not, and the reverse-DNS name (`getent hosts <address>` or `nslookup`) in the N4 report. Report8 did not record the address, so a repeat could not be told from the first; this time also record the decoded address in the N4 report (a node egress address, not a secret). The one-liner reads IPv4 only; also decode `/proc/net/tcp6` by hand as described above. report8 saw a non-RFC1918 address, which may be public or another non-private range.

The credential key rule (case-insensitive substring match, RE2, the same in every statement; RE2 has no lookahead, so `token` is anchored to the end of the key):
`(?i)(secret|passw|pwd|authorization|cookie|credential|passphrase|jwt|bearer|api[._-]?key|private[._-]?key|access[._-]?key|signing[._-]?key|ssh[._-]?key|session[._-]?id|token$|token[._-]?(value|id|string)$)`.
A key is deleted when it CONTAINS (any letter case, with or without a `.`, `_` or `-` between the words) `secret`, `passw` (so `password`, `passwd`, `passwords`), `pwd`, `authorization`, `cookie`, `credential`, `passphrase`, `jwt`, `bearer`, `api_key`, `private_key`, `access_key`, `signing_key`, `ssh_key` or `session_id`, or when it ENDS in `token` or in `token_value`/`token.id`/`token_string`. This covers camelCase and joined names: `githubToken`, `sessionToken`, `apiToken`, `csrfToken`, `jwtToken`, `clientSecret`, `secretKey`, `dbPassword`, `xApiKey`, `privateKey`, `sshKey`, `sessionId`. Kept (tested through the real collector in every context): `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.usage.total_tokens`, `gen_ai.request.max_tokens`, `max_tokens`, `tokens`, `token_count`, `token.count`, `tokenizer`, `token_type`, `geldar.run_id`, `prompt.sha256`, `http.response.status_code`, `gen_ai.response.finish_reasons`, `gen_ai.prompt`. Gap by design: a credential held under a key that carries none of these words (for example `sid`, `auth`, `key`) is not caught: the rule is on key names, not values. The test that proves the lists (logs, spans, span events, datapoints of gauge, sum and histogram, resource, scope and map-body keys all behaved the same) is described in G1.

IPv4: each octet 0 to 255, four parts, with digit and dot only as boundaries: an address glued to a word is masked (`ip_203.0.113.1` becomes `ip_<addr>`, `addr_198.51.100.5`, `x203.0.113.4`, `203.0.113.4abc`), and a trailing sentence dot is fine (`at 203.0.113.1.`). A three-part version (`1.20.4`), a longer dotted number (`203.0.113.4.5`, `203.0.113.4.5.6.7.8`, `203.0.113.1.5`) and out-of-range octets (`999.0.113.1`, `256.0.113.1`) are kept. A genuine four-part number that is not an address (a four-part version-like string, `203.0.113.1000` is kept because 1000 is out of range) is masked: documented caveat. The match consumes one neighbour character, so each IPv4 statement is repeated once in `gateway.yaml` to catch addresses separated by a single character (`203.0.113.1 203.0.113.2 203.0.113.3` is masked whole). Tested through the real collector on 25 inputs in the log body, a map body value, resource attributes and span event attributes, with identical results.

IPv6 compressed form: `::1`, `fe80::1:2`, `2001:db8::1`, `1::`, `10:20::30` and `[2001:db8::1]:25565` are masked; `Cache::get`, `std::vector`, `Foo::Bar::baz`, `end::` and `12:30:45` are kept. A word made only of hex letters on both sides of `::` (`a::b`, `face::cafe`) is masked: it is also a valid IPv6 address, and the rule prefers masking.

### Limits (exact values)

- Request size, gateway to SigNoz collector: the batch processor is capped at 256 items (`send_batch_size` and `send_batch_max_size`), and the exporter batches by bytes (`sending_queue.batch`, `sizer: bytes`, `min_size` 1048576, `max_size` 12582912, `flush_timeout` 5s): no exported request is larger than 12 MiB (OTLP proto size, before gzip). The SigNoz collector's gRPC receiver is raised to `max_recv_msg_size_mib: 32` in `signoz-otelcol-config.yaml` (key accepted by the v0.144.6 image, a misspelt key makes it refuse to start). That collector must be RESTARTED to apply it, and BEFORE the gateway starts: at the 4 MiB default a request above 4 MiB is refused for good and dropped. The gateway's own receivers are set explicitly: OTLP/HTTP `max_request_body_size` 16 MiB and gRPC `max_recv_msg_size_mib` 16 (the Caddy ingest cap is 8 MiB).
- A single log record cannot be split, so `batch.max_size` must exceed the largest record: 12 MiB covers the 8 MiB Caddy cap with overhead. Tested locally on 0.164.0 against a stand-in downstream with a 32 MiB receiver, through the real `gateway.yaml`: 60 records of 100 KB in one request (60/60), one record of 3.5 MiB, one of 5 MiB and one of about 8 MB (1/1 each) all arrived. A record above 12 MiB cannot reach the gateway through Caddy; if one arrived directly the batcher drops it and logs `Failed to split request ... single log record exceeds the max size limit`.
- Memory under load: the container cap is 1 GiB (`mem_limit` and `memswap_limit` 1g), `memory_limiter` `limit_mib` 800 / `spike_limit_mib` 160 and `GOMEMLIMIT=800MiB` (80% of the cap). Tested locally at these settings: 60 parallel posts of 3 MiB (1800 records): all `200`, 1800/1800 delivered, peak container memory 642 to 713 MiB (docker stats, 0.3 s polling), no OOM kill. 20 parallel posts of 6 MB (1200 records): all `200`, nothing lost (1575 records arrived: a few requests were exported twice after the stand-in downstream was slow, which is at-least-once delivery), peak 729 MiB, no OOM kill. For comparison the earlier 512m cap was OOM-killed by 100 parallel 6 MB posts. The real bound is the Caddy body cap (8 MiB per request) times the number of concurrent requests; `restart: unless-stopped` brings the container back after an OOM kill, the persisted queue survives, and a request in flight at that moment was never acknowledged, so it is not silently lost (the producer sees a connection reset).
- Retry: `retry_on_failure.max_elapsed_time: 0`, so a failed export is retried (with backoff) until it is delivered. The queue size below, not a retry limit, is what bounds a downstream outage.
- Queue and outage (measured, not assumed): `sending_queue.sizer: bytes`, `queue_size: 268435456` (256 MiB of queued request data) per signal queue; there are THREE queues (traces, logs, metrics), persisted by `file_storage` in `/mnt/nvme/geldar-telemetry/queue`. Queued items are also held in the heap (earlier measurement: about 0.75 to 0.9 x the queued bytes), so a 1 GiB queue was never reachable: the memory limiter refused data (503) at about 100 to 400 MB queued under the old 512m cap. At 256 MiB per queue the bound sits under the limiter's soft limit (800 - 160 = 640 MiB). With the SigNoz collector or ClickHouse down, the gateway therefore holds about 256 MiB of telemetry per signal; after that the exporter drops new data, logs `sending queue is full` at error level, and the producer STILL gets `200` (the batch processor is asynchronous). A producer SDK's own retry sits outside this and cannot see the loss. Local outage test at the shipped settings (downstream stopped, 140 posts of 3 MB = 4200 log records of about 420 MB, all answered `200`, no 503): 2566 records (about 257 MB) were queued, 1634 were dropped and counted in `otelcol_exporter_enqueue_failed_log_records` (1634), 14 `sending queue is full` lines were logged; the container held 445 MiB (peak 629 MiB while posting), the queue directory was 414 MB (1.6 x the queued bytes); after the downstream was started again all 2566 queued records were delivered (2625 arrived: some requests were exported twice). If all three queues fill at once the heap can reach the limiter's soft limit and the limiter answers 503 (visible to the producer); that case was not tested.
- Disk: three queues x 256 MiB x about 1.9 file overhead (measured 1.5 to 1.9; 1.6 in the test above; the bbolt file does not shrink after a drain) is about 1.5 GiB worst case on the shared `/mnt/nvme`. The directory is NOT a fixed-size volume. Decision 0352 and collector-options F2 describe the gateway queue as a fixed-size volume (`gateway-queue`) with the bytes sizer only after a soak test; this deviates on both points and needs the owner's acceptance: it uses the plain N3 directory `/mnt/nvme/geldar-telemetry/queue` and the bytes sizer, with 256 MiB per queue and about 1.5 GiB worst case as the bound. The `/mnt/nvme` filesystem alarm (collector-design section 8, not built yet) is required, and verification step 8 checks the size with `du`.
- Losses are visible in SigNoz: the gateway scrapes its own metrics (`127.0.0.1:8888` inside the container, `prometheus` receiver, every 30 s) into the metrics pipeline, so these arrive downstream (checked locally: `otelcol_exporter_queue_size`, `otelcol_exporter_queue_capacity` and `otelcol_exporter_enqueue_failed_log_records` reached the stand-in). Counters appear only after their first increment (`otelcol_exporter_send_failed_*` and `otelcol_processor_refused_*` do not exist until something fails). Alarms to build on them: `otelcol_exporter_enqueue_failed_log_records`, `..._spans` or `..._metric_points` rising above 0 (data dropped, queue full); `otelcol_exporter_send_failed_*` rising (the downstream is rejecting); `otelcol_processor_refused_*` rising (memory limiter, producers get 503); `otelcol_exporter_queue_size / otelcol_exporter_queue_capacity` above 0.8 for 10 minutes (an outage is filling the queue); and the `/mnt/nvme` free-space alarm. A gateway restart resets the counters (the queue itself persists). The loss is also in `docker logs geldar-gateway` (json-file 10m x 3, rotates). During an outage `level: warn` shows only the exporter's `connection refused` lines; a DNS failure of the downstream name logs nothing.

### Order dependencies

- The SigNoz collector (N7, `geldar-signoz-otelcol`, OTLP gRPC on 4317) must be up before ingested data is useful. The gateway may start before it: the exporter retries until delivered and the queue is persisted in `/mnt/nvme/geldar-telemetry/queue`.
- The Caddy ingest route (N14) targets the gateway's loopback publish `127.0.0.1:4320`, so the gateway must run before the route is loaded.
- `GELDAR_TELEMETRY_URL` on the Geldar services (a later batched Body redeploy, not applied now) is intended to be `http://geldar-gateway:4318` (OTLP/HTTP; the container name, which Docker DNS resolves on both `geldar-colo` and `geldar-telemetry`; there is no `otel-gateway` alias).

### Failure and rollback

- Failure: `docker logs geldar-gateway`; a config error stops the container at start (restart loop): stop it and fix the file.
- Note for every `compose.yml`-only command in this README (stack down, rollback, status): the gateway belongs to the same project `geldar-telemetry`, so a `compose.yml`-only call leaves it as an orphan and warns about it. Add `-f deploy/telemetry/compose.gateway.yml` to those calls when the gateway exists.
- Rollback: `docker compose -f deploy/telemetry/compose.yml -f deploy/telemetry/compose.gateway.yml stop geldar-gateway` then `docker compose -f deploy/telemetry/compose.yml -f deploy/telemetry/compose.gateway.yml rm -f geldar-gateway`. The queue directory contents are disposable (`rm` the files inside only on the owner's say). Removing the container unpublishes `127.0.0.1:4320`, which removes the Caddy route's target (the route then returns a gateway error until it is switched off with `otel-off.caddy`).
