## Secrets

Sudo scope for the node steps: `mkdir` and `chown` inside `/mnt/nvme/geldar-telemetry` only. Anything else (including `sudo stat`, `sudo cat`, and files in `/tmp`) must be asked for first.

Passwords are never inline. Compose mounts them as file secrets from `/mnt/nvme/geldar-telemetry/secrets/`:

- `ch_writer_password`: the writer password. Used by the migrator and the collector.
- `ch_reader_password`: the reader password. Used by the query service.
- `ch_signoz_admin_password`: the retention user's password (D3). Created only for the retention window; used only through `compose.retention.yml` (see "Retention window (N6c)"). Not referenced by `compose.yml`.

**Password format (S-E):** each password is 32 random bytes as 64 lowercase hex characters (`[0-9a-f]` only, for example `openssl rand -hex 32`). No other characters: the value is placed in a `tcp://user:password@host` URL, where `@ / : ? # %` break the parse. Each file has no trailing text; `$(cat)` strips the final newline.

**File owner and mode.** Compose ignores `uid`, `gid` and `mode` on file secrets on a non-Swarm engine `[INF]`, and this compose file does not set them. The container sees the host file's owner and mode. Create the files with the owner and mode below, then check with `ls -ln` (see item 14). The owner is numeric because the container has no name for it.

| File (host) | Read by | Runs as | Required owner:mode |
|---|---|---|---|
| `secrets/ch_writer_password` | `geldar-signoz-migrator`, `geldar-signoz-otelcol` (wrapper) | uid 10001 (image `User`) | `10001:10001` `0400` |
| `secrets/ch_reader_password` | `geldar-signoz` (wrapper) | uid 0 (root, no USER; `cap_drop: ALL`, so no DAC_OVERRIDE) | `0:0` `0400` |
| `secrets/ch_signoz_admin_password` | `geldar-signoz` (wrapper) only while `compose.retention.yml` is applied | uid 0 (same as the reader) | `0:0` `0400` |
| `secrets/ch-hashes.env` | the compose client, which passes it to `geldar-ch` as env (`env_file`); no container reads the file | the operator running compose | operator's own uid, `0400` |

A reader file owned by 10001 would be unreadable to `geldar-signoz` (root without DAC_OVERRIDE cannot read a 0400 file owned by another uid); a writer file owned by root would be unreadable to 10001.

### Password hashes

`clickhouse/users.d/users.xml` is well-formed and contains no hash. Each user reads its hash with `<password_sha256_hex from_env="..."/>`: `GELDAR_CH_WRITER_SHA256` (writer), `GELDAR_CH_READER_SHA256` (reader) and `GELDAR_CH_SIGNOZ_ADMIN_SHA256` (the retention user `geldar_signoz_admin`). That is THREE hashes. The admin user is used only in the retention window, but `users.xml` requires its hash for as long as the user is defined there (a missing variable is a start failure). `geldar-ch` loads them from `/mnt/nvme/geldar-telemetry/secrets/ch-hashes.env` (compose `env_file`, not in git). Write that file on the node, mode 0400, with three lines `GELDAR_CH_WRITER_SHA256=<hex>`, `GELDAR_CH_READER_SHA256=<hex>` and `GELDAR_CH_SIGNOZ_ADMIN_SHA256=<hex>`; the first two come from step e (N4), the third from the "Third hash" block below. Make each hex of the first two with the guarded form below, run it as the account that can read both 0400 secret files, as at N4 step e (the third-hash block below reads no root-owned file and runs as the ssh user, uid 1001). The form stops on an empty or short password, so an unreadable file cannot produce a hash:

```
pw=$(cat /mnt/nvme/geldar-telemetry/secrets/ch_writer_password) && [ "${#pw}" -eq 64 ] && printf %s "$pw" | sha256sum | cut -d' ' -f1
```

Use the same form for `ch_reader_password`. If a command prints nothing or exits non-zero, stop and do not write that hash. The hash `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855` is the SHA-256 of the empty string (what an empty password would give); if it appears in `ch-hashes.env`, delete that file and start again. Do not put the values in a command line that is saved in shell history.

- **Third hash (D3).** `users.xml` also defines `geldar_signoz_admin`, whose hash is `GELDAR_CH_SIGNOZ_ADMIN_SHA256` (a third line in `ch-hashes.env`). Compose needs no change for it: `env_file` already passes the whole file to `geldar-ch`, and no value is in the repo. **Ordering (a start failure otherwise):** with `from_env` for an unset variable, `geldar-ch` refuses to start ("Env variable is not set", seen on the node). So once the new `users.xml` is on the node, `geldar-ch` cannot be restarted until `ch-hashes.env` holds this line. Do these in order: (a) and (b) in the one guarded block below, which creates `secrets/ch_signoz_admin_password` (64 hex, `0:0` `0400` as the reader file, per the table in "Secrets"), computes the hash from the shell variable, and appends the third line to `ch-hashes.env`, BEFORE the new `users.xml` reaches the node; the node's `users.xml` is staged from a tarball under `/mnt/nvme/geldar-telemetry/src`, so re-staging is a node step; (c) restart `geldar-ch` (`docker compose -f deploy/telemetry/compose.yml up -d --force-recreate geldar-ch`; the env file is read at container creation, so a plain restart does not pick up the new line). Whether ClickHouse reloads `users.d` without a restart is `[UNV]` (item 36); plan a recreate at a time when nothing depends on `geldar-ch` (stop `geldar-signoz` and `geldar-signoz-otelcol` first, or accept their reconnect); (d) verify: `docker inspect -f '{{.State.Health.Status}}' geldar-ch` prints `healthy`, and `docker exec geldar-ch clickhouse-client -q "SELECT name FROM system.users ORDER BY name"` lists `geldar_signoz_admin`. Mirror rule for removal: never delete the hash line while `users.xml` on the node still names it (see the teardown order in "Retention window (N6c)", step 8).
- **Third hash block.** Run as the ssh user that owns `ch-hashes.env` (uid 1001, mode 0400), from any directory. It never reads the root-owned reader file and no secret is in argv:
  ```
  (
  set -eu
  cd /mnt/nvme/geldar-telemetry/secrets
  umask 277
  [ "$(stat -c %u ch-hashes.env)" = "$(id -u)" ] || { echo "ABORT: ch-hashes.env is not owned by the current uid" >&2; exit 1; }
  [ -w . ] || { echo "ABORT: secrets/ is not writable" >&2; exit 1; }
  if [ -n "$(tail -c1 ch-hashes.env)" ]; then chmod u+w ch-hashes.env; printf '\n' >> ch-hashes.env; chmod 0400 ch-hashes.env; fi
  empty=e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
  [ ! -e ch_signoz_admin_password ] || { echo "ABORT: ch_signoz_admin_password exists" >&2; exit 1; }
  if grep -q '^GELDAR_CH_SIGNOZ_ADMIN_SHA256=' ch-hashes.env; then echo "ABORT: hash line exists" >&2; exit 1; fi
  pw=$(openssl rand -hex 32)
  [ "${#pw}" -eq 64 ] || { echo "ABORT: password is not 64 characters" >&2; exit 1; }
  h=$(printf %s "$pw" | sha256sum | cut -d' ' -f1)
  if [ -z "$h" ] || [ "${#h}" -ne 64 ] || [ "$h" = "$empty" ]; then echo "ABORT: empty or bad hash" >&2; exit 1; fi
  printf %s "$pw" > ch_signoz_admin_password
  chmod u+w ch-hashes.env
  printf 'GELDAR_CH_SIGNOZ_ADMIN_SHA256=%s\n' "$h" >> ch-hashes.env
  chmod 0400 ch-hashes.env
  )
  sudo -n chown 0:0 /mnt/nvme/geldar-telemetry/secrets/ch_signoz_admin_password
  ls -ln /mnt/nvme/geldar-telemetry/secrets/ch_signoz_admin_password /mnt/nvme/geldar-telemetry/secrets/ch-hashes.env
  grep -c '^GELDAR_CH_SIGNOZ_ADMIN_SHA256=' /mnt/nvme/geldar-telemetry/secrets/ch-hashes.env
  ```
  Expected: the password file is `0 0` `-r--------`, `ch-hashes.env` is `1001` (or the ssh user's uid) `-r--------`, and the count is `1`. On `ABORT` or any non-zero exit, delete `ch_signoz_admin_password` if it was created, check that `ch-hashes.env` has no `GELDAR_CH_SIGNOZ_ADMIN_SHA256` line or restore its mode to 0400, and start again. Sudo scope: only `mkdir` and `chown` inside `/mnt/nvme/geldar-telemetry`; there is no `sudo cat` or root read. Guards in the block: the `stat -c %u` owner check aborts when the file is not owned by the current uid; `secrets/` must be writable; a missing final newline in `ch-hashes.env` is fixed with `printf '\n'` first (no value in argv), so the new line is not glued to the previous one. Node check before running it: `ls -ldn /mnt/nvme/geldar-telemetry/secrets` and `ls -ln /mnt/nvme/geldar-telemetry/secrets/ch-hashes.env` must show the ssh user as owner of the file and write access to `secrets/` (the block creates `ch_signoz_admin_password` there). The hash is computed from the variable before the `chown`, which is why no step needs to read the file as root. This block was not run on the node `[UNV]`.
- `from_env` in ClickHouse config is `[INF]`, unverified on 25.12.5. **Blocks start of geldar-ch** (a missing variable is a start failure, which fails closed).
- Residual exposure: the hash is in the container environment, so `docker inspect geldar-ch` shows it to anyone with Docker access. A sha256 of a password can be brute-forced offline. Docker access is root-equivalent on this host, so this is accepted, not removed.

### Secret wrappers (migrator, SigNoz, collector)

The DSNs are built by a short shell wrapper that reads the secret file at start (see the compose `command:` lines). The wrapper text contains `$(cat /run/secrets/...)`, not the value, so no password is in argv or in `docker inspect`. The value lives in the environment of the running process, which is readable by root and by the same uid through `/proc/<pid>/environ`. That residual exposure is accepted for this single-node host. The migrator uses the collector image (`signoz/signoz-otel-collector`, see the Pins), so its DSN is an environment variable, as the SigNoz `migrate` subcommands expect. The wrapper relies on `/bin/sh` in the image: `[UNV]` for the collector and the SigNoz image is alpine.

No secret value, token or account name is in this directory.

## Healthchecks and restarts

Compose gates start on health. `geldar-ch` waits for `geldar-ch-keeper` to be healthy. The migrator, `geldar-signoz` and `geldar-signoz-otelcol` wait for `geldar-ch` to be healthy. So a failing Keeper healthcheck stops `geldar-ch` from starting, and a failing ClickHouse healthcheck stops the migrator, SigNoz and the collector from starting. The blocked services are not restarted and do not start at all.

Nothing restarts a service because of a healthcheck: plain Docker does not act on `unhealthy`, and there is no autoheal sidecar. Restart loops (`restart: unless-stopped`) come only from a process exit, for example a ClickHouse config parse error. Those do not damage data.

## Retention window (N6c)

Why: SigNoz v0.148.1 sets retention through its own API, `POST /api/v1/settings/ttl?type=traces|logs|metrics&duration=<h>` (admin only). SigNoz then runs `ALTER TABLE ... ON CLUSTER ... MODIFY TTL` on 7 traces, 4 logs and 8 metrics tables over its own ClickHouse connection, which is the DSN in compose, `geldar_reader` (readonly=2, SELECT only, cannot run DDL). The owner ruled (D3, geldar-93, 2026-11-16, "temporary override accepted"): do not widen the reader; use the dedicated user `geldar_signoz_admin` (ALTER TTL, SELECT and CLUSTER grants only), swapped in by `compose.retention.yml` for the window, then removed. Source of the API facts: research on the SigNoz v0.148.1 source, and round 9 (local scratch run, ClickHouse 25.12.5, SigNoz v0.148.1; not the node), whose results are cited below as "round 9".

**Blast radius.** `ALTER TTL` on `signoz_traces`, `signoz_logs` and `signoz_metrics` can delete telemetry rows in those three databases (a short TTL expires them), and `geldar_signoz_admin` is not readonly (`readonly=0`), so SQL sent over SigNoz's ClickHouse connection while the override is on is not read-only. Whether SigNoz passes non-SELECT SQL through its raw ClickHouse query type is not known `[UNV]`. So the window is closed in the same session it is opened in. To detect an override left in place: (a) `docker inspect -f '{{.Config.Cmd}}' geldar-signoz | grep -c geldar_signoz_admin` prints `0` once closed (the DSN user is in the command, not the password); (b) `docker compose -f deploy/telemetry/compose.yml config | grep -c geldar_signoz_admin` prints `0` (base file only; run from the repo checkout root); (c) `docker exec geldar-ch clickhouse-client -q "SELECT user, count() FROM system.query_log WHERE event_time > now() - 600 GROUP BY user"` shows no `geldar_signoz_admin` rows after the window ended (non-reader queries from `geldar-signoz` mean the override is still on). A plain `docker compose -f deploy/telemetry/compose.yml up -d geldar-signoz` without the override changes the `command` and so recreates `geldar-signoz` on the reader.

**Preconditions.** (1) N6b done: the first admin account exists in SigNoz (its credentials are held by the owner, not in the repo). (2) `geldar-signoz` is running on the reader (`docker inspect -f '{{.State.Health.Status}}' geldar-signoz` prints `healthy`). (3) D3 secrets are present: `ls -ln /mnt/nvme/geldar-telemetry/secrets/ch_signoz_admin_password` shows `0 0` and `-r--------`, `ch-hashes.env` has the third line (`grep -c '^GELDAR_CH_SIGNOZ_ADMIN_SHA256=' .../ch-hashes.env` prints `1`; do not print the file), `geldar-ch` was recreated after that (see "Password hashes", ordering), and `system.users` lists `geldar_signoz_admin`. (4) `docker compose version` is 2.24.0 or later (`!override` and `required: false`). (5) Nothing else is writing a retention change (SigNoz answers 409 while one is pending).
